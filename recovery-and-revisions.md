# Drag-and-Drop Corruption and Revision Recovery

Full detail for Step 2b in SKILL.md. See the First Rule in SKILL.md for the standing rule this supports — this file covers why drag-and-drop saves are risky on a raw-shortcode-built page, and how to recover if one happens.

## Two Edit Surfaces for the Same Page

**WPBakery Page Builder itself is the risk here, not Gutenberg.** A page built by this skill is written as a raw shortcode string and pushed straight into `post_content` via REST, or via the native WP text editor view that WPBakery calls "Classic Mode" (that toggle exits WPBakery's own builder UI and shows the literal `[vc_row]...[/vc_row]` text). WPBakery *also* ships a separate drag-and-drop visual "Backend Editor" (reachable via `?wpb-backend-editor` or the page-builder toggle in wp-admin) that renders those same shortcodes as draggable visual elements, backed by a live in-browser Backbone model (`window.vc.shortcodes` — the same object `cz-elements.md`'s `singleStringify()` technique uses read-only to construct shortcode strings safely). **Opening a page in that drag-and-drop editor and clicking Update/Save is a confirmed way to corrupt the page — a user's own words: "IF I EDIT THE BLOCKS THE WHOLE SITE EXPLODES."** Two distinct, real mechanisms explain why:

1. **Whole-tree re-serialization, not a patch.** The drag-and-drop editor doesn't save just the one element you touched — on Update it re-serializes WPBakery's *entire* in-memory shortcode model for the page back into `post_content`. Any construct in the existing raw string that the visual UI wouldn't normally produce on its own — a `<style>`-only carrier row with no visible content, a `cz_*` theme-native element assembled via the `singleStringify` technique instead of real UI clicks, an attribute/value combination the builder's param UI doesn't expose a control for — is exactly the kind of content a round-trip through that model risks dropping, reordering, or mangling on save, even if you touched an unrelated element.
2. **`max_input_vars` truncation on large pages.** WPBakery's backend editor submits the whole page as one large form post, one field per shortcode parameter. A big multi-section page (very plausible for a full XD-cloned homepage) can exceed PHP's default `max_input_vars` (1000), which silently truncates the trailing form fields rather than erroring — this is a documented, independent WPBakery failure mode (not specific to this skill's raw-string approach) that resets/drops elements on save. It compounds the re-serialization risk: a page assembled by this skill, with many rows/columns/shared-style carriers, is squarely the shape of page most likely to hit this limit.

Because the shared `<style>` carrier row's CSS affects the whole page (and, if global chrome CSS ever ended up in page content instead of Additional CSS — see `customizer.md` — potentially more than one page), a single bad Update from the drag-and-drop editor can visibly break the page's layout/styling.

**Practical rule: once you've built or edited a page's content as a raw shortcode string, do not open that page's drag-and-drop Backend Editor and click Update/Save yourself, even to "just check how it looks."** Viewing the live front-end page, or opening WPBakery's own Classic Mode / the text editor view (which shows/edits the same raw string you wrote, not a re-serialized version), is safe. Opening the drag-and-drop visual canvas and interacting with it (dragging, resizing, editing an element's settings panel) followed by any Save is the unsafe path.

**Tell the user explicitly, in your own words, at the end of any build/edit on an unrepaired legacy WPBakery page — this matters most the first time you build a page this way for a given site:** "This page's content was written directly as WPBakery shortcode text, not built through the drag-and-drop visual builder. If this page's editor is opened in drag-and-drop mode — dragging elements, editing them in the visual canvas — and then Update is clicked, WPBakery re-serializes the whole page from its own model and can silently break the layout or styling, especially on a page this large. To edit safely afterward, use WPBakery's Classic Mode / text editor view, or come back and ask me to edit the raw shortcode, instead of the drag-and-drop builder." Per the First Rule in SKILL.md, the actual goal is to repair the page so this warning becomes unnecessary — this warning is for pages not yet repaired.

## Recovering From a Bad Drag-and-Drop Save

**If a page was opened in drag-and-drop mode and saved, and something now looks broken: recover from WordPress's own revision history — it's REST-reachable and does not depend on this session (or any prior session) having kept a snapshot.** Confirmed working end-to-end via Application Password REST auth alone, no browser tooling needed:

1. List revisions for the page: `GET /?rest_route=/wp/v2/pages/{id}/revisions` (or `/wp/v2/posts/{id}/revisions`). Returns every saved revision — including autosaves and Update-button saves from *any* editor (Classic text view, REST, or the drag-and-drop builder) — each with `id`, `date`, `author`, `parent`. A homepage with ~2 weeks of edits had 49 revisions retained in one real project.
2. Fetch a specific revision's raw content: `GET /?rest_route=/wp/v2/pages/{id}/revisions/{revision_id}&context=edit` (the `context=edit` query param is required — the default context omits the `raw` field and only returns `rendered` HTML, which is post-shortcode-processing and not directly restorable). The response's `content.raw` is the exact `post_content` string as it existed at that revision — full raw WPBakery shortcode text, byte for byte.
3. **Identify the last good revision before the drag-and-drop save by date, not by guessing which one "looks right" from a truncated preview** — pull a few candidates around the suspected break time and grep each one's `content.raw` for a known marker (a specific `el_class` name, a distinctive piece of copy) to confirm which side of the break each revision falls on.
4. Restore by pushing that revision's raw content back as the page's own current content: `POST /?rest_route=/wp/v2/pages/{id}` with `{"content": "<the raw string from step 2>"}`. This does not "revert" via any special WordPress revision-restore endpoint (there isn't a public REST one) — it's a normal content update using old content as the new value, exactly like any other push this skill makes.
5. Verify the same way as any other push (Step 5 in SKILL.md) — screenshot the live front-end at desktop and mobile widths — since the corruption's exact edges may not be obvious from the raw string alone.

This is a materially better recovery path than trying to diff against a remembered "last known-good" string, because it works even when no snapshot exists in the current conversation (a prior session's work, or a user's own drag-and-drop edit that happened with no assistant involved at all) — the revision history already has it. **A useful preventive habit given this exists: before making a large or risky change to an already-working page (a full-content rewrite, a big section replace), it costs one extra `GET` to fetch and locally note the current revision `id`/date first**, so a fast rollback target is already known rather than needing to search through possibly dozens of revisions after the fact.
