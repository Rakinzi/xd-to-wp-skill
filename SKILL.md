# XD Design to WordPress (WPBakery)

## First Rule: WPBakery Drag-and-Drop Saves Must Preserve the Page

## Reuse Similar XD Components as Page Templates

When multiple XD artboards or sections share the same visual structure, do not rebuild each one from scratch. Treat the first well-tested WordPress/WPBakery implementation as the reusable template, duplicate that shortcode/CSS pattern, then change only the page-specific copy, images, links, post queries, and active menu state. This keeps spacing, responsive behavior, builder compatibility, and global styling consistent across the site.

- Before building multiple pages, classify the XD artboards into repeated patterns: shared header/top bar/footer, inner-page hero, two-column story block, metric/stat section, card/listing grid, CTA band, and document/news/post archive.
- Reuse the proven WPBakery structure for each pattern instead of inventing new wrapper classes or layouts per page. If the Home hero, inner-page hero, report grid, or post grid already passed desktop/mobile/editor checks, copy that structure and adjust only the content inputs.
- For repeated content lists, keep the source CMS-native: real WordPress posts for news/announcements and real reusable listing structures for reports/downloads. Do not hand-type repeated cards just because copying markup is faster.
- Keep shared chrome global and page sections page-scoped: menu/top-bar/footer/dropdown rules can be global; per-page hero/card/content rules belong in that page’s native WPBakery Custom CSS field.
- After cloning a pattern, verify the custom classes still attach to the rendered DOM and the copied responsive rules still apply. A cloned section is not done until the changed copy/assets render correctly at desktop and mobile widths.

Build and repair pages so the user can add, edit, and move native WPBakery elements and click Save/Update without corrupting the styles. A page that only works when edited as raw shortcode text is unfinished when visual editing is required. This rule takes precedence over the legacy raw-shortcode and CSS-carrier workarounds below.

- **Never store a page stylesheet inside a Text Block (`vc_column_text`).** In this site's revision history, an editor save inserted 91 `<br />` tags into that block's CSS and broke the stylesheet. Use WPBakery's native per-page Custom CSS field for page styling; use the theme's global styling facilities for shared site styles. Obtain a real wp-admin session when the native field is unavailable through REST; an Application Password alone does not provide browser login access.
- Back up current content and CSS before migration. Test the repair on a draft copy first, preserving existing sections and user additions. Remove the old stylesheet carrier only as part of saving the CSS into its native field.
- Use valid native row/column nesting and explicit spacer elements or design options. Do not depend on stray newlines or `<br>` elements between shortcodes for spacing: the builder can normalize them away on save.
- **Content-only REST updates can erase native per-page CSS on this stack.** This occurred after migrating the test page to WPBakery 9.0.1's Custom CSS field. Once that field holds the stylesheet, prefer the authenticated editor save that includes both content and CSS. Before any alternative update, back up the field and verify afterward that it survived; never assume an unchanged REST payload preserves unexposed plugin metadata.
- Verify an actual visual-editor round trip: add a block, move it, save, reload the editor, and inspect the live preview at desktop and mobile widths. Confirm the move persisted, the CSS is intact, and section styling and spacing remain correct. A successful REST response, unchanged CSS alone, or a drag tool reporting success without an actual order change is insufficient. Only apply the tested repair to the original after these checks pass.
- The warnings below about avoiding visual-editor saves apply to **unrepaired legacy pages**, not the intended final workflow. Do not substitute “use Classic Mode forever” for making the user's drag-and-drop workflow work. If a limitation remains, state exactly what is unverified or still breaks.

## Overview

Turns an Adobe XD prototype URL into a live WordPress page: capture the design via headless browser, build it as native WPBakery shortcodes (not raw HTML), push via REST API. Core principle: WPBakery shortcodes are editable in wp-admin's visual builder; a single `wp:html`/raw-HTML blob is not — always prefer real shortcodes/blocks over HTML dumps when the destination has a builder.

## When to Use

- User shares an `xd.adobe.com/view/...` link and asks to build/clone it as a WordPress page
- Site has WPBakery (`js_composer`) active — check `wp/v2/plugins` first; if a different builder or block theme is active, the capture steps still apply but the build step differs (see Adapting section)
- Rebuilding a page that was previously hand-rolled as HTML and needs to become builder-editable

## Step 1: Capture the Design

XD prototypes render on a `<canvas>`-adjacent scrollable `<div>`, not the page body — `document.body.scrollHeight` will lie (often near-zero or one viewport tall).

1. Open the XD URL with chrome-devtools-mcp `new_page`, timeout 45000ms (cold loads can exceed the default 10s and falsely report failure while actually still rendering)
2. Find the real scroll container:
   ```js
   Array.from(document.querySelectorAll('*'))
     .filter(el => el.scrollHeight > el.clientHeight + 50 && el.clientHeight > 200)
   ```
   Look for an element like `#scroll-1` with `scrollHeight` much larger than `clientHeight`.
3. Set `scrollTop` on that element (not `window.scrollTo`) in increments ~ viewport height, `sleep 1` after each, screenshot each step. `take_screenshot fullPage:true` does NOT work here since the real content isn't in document flow.
4. From the screenshots, note: section order, colors (hex if visible), copy text verbatim, image subjects (you'll substitute stock/placeholder images — XD-hosted images aren't fetchable), any empty/placeholder states in the original design (e.g. a card grid with only one card populated — reproduce that faithfully, don't invent fake content for empty slots).
5. **Scroll-triggered fade-in animations can make a section look wrong or empty on the first screenshot after landing on it.** XD prototypes commonly animate cards/images in as they enter the viewport (opacity 0 → 1, sometimes with a color/position shift mid-transition). A screenshot taken immediately after `scrollTop` can catch elements mid-fade — pale/washed-out colors, missing icons, empty-looking cards — that look like real design content (e.g. a card row appeared to be light lavender before a coincidental second capture, ~1-2s later, revealed the true solid navy). Always `sleep` 1-2s after scrolling to a new section before screenshotting, and if anything still looks unfinished/faded, re-screenshot again before concluding it's the actual design — don't trust the first frame.
6. **Interactive elements (nav dropdowns, mega-menus, tabs) may or may not be modeled in the XD file as real click-through hotspots.** Don't assume a `:hover` CSS state on your build is equivalent to — or exempt from checking against — the XD. First check whether XD models the interaction at all: click the relevant hotspot for real (see the click-mechanics note below) and see if it navigates to a linked "open" state screen. If it does, that linked screen is the actual design reference — measure it properly (exact panel width/height/position via the screenshot-to-viewport scale factor: screenshot pixels × (real viewport width ÷ screenshot width) = real CSS pixels) rather than guessing proportions from general site styling. If no linked screen exists (clicking does nothing), then no reference exists and it's fair to design the interaction consistent with the rest of the site's visual language — but say so explicitly rather than silently presenting an invented style as if it were XD-verified.
   - **XD hotspots need real pointer event sequences, not a bare synthetic `click`.** A single `element.dispatchEvent(new MouseEvent('click', {...}))` on the element under the target coordinates (found via `document.elementFromPoint(x, y)`) is usually not sufficient to trigger XD's own interaction handling — it did not fire a linked-screen navigation in this project even though a real navigation did exist. Dispatch the fuller sequence instead: `pointerdown` → `mousedown` → `pointerup` → `mouseup` → `click`, all as bubbling/cancelable events with matching `clientX`/`clientY` (and `pointerId`/`isPrimary` on the Pointer events) at the same coordinates. Compute those coordinates by taking a screenshot, visually locating the target in screenshot-pixel space, then converting to real CSS pixels with the scale factor above (get real viewport dimensions from the scroll container's `getBoundingClientRect()`, e.g. `document.getElementById('scroll-1').getBoundingClientRect()`) — do not click at raw screenshot-pixel coordinates directly, since the screenshot is rendered at a different (often ~1.4-2x) scale than the live viewport.
   - XD's own DOM/accessibility tree is opaque (a single unlabeled `generic` node covering the whole canvas) — `take_snapshot` will not give you clickable element references the way it does on a normal webpage. Coordinate-based clicking via `elementFromPoint` is the only reliable approach for XD prototypes specifically.

## Step 2: Confirm the Target Stack Before Building

Don't assume the theme or builder — it can change mid-task (as installing WPBakery did here). Always check immediately before writing content:

```bash
curl -s -u "user:app-password" "http://SITE/?rest_route=/wp/v2/plugins" | grep -E "js_composer|status"
curl -s -u "user:app-password" "http://SITE/?rest_route=/wp/v2/themes" | python3 -c "import json,sys; [print(t['stylesheet'],t['status']) for t in json.load(sys.stdin)]"
```

If `js_composer` is `active` → build with VC shortcodes (Step 3). If a block theme is active with no page builder → use native Gutenberg block comments instead of raw `wp:html`, and be aware block themes wrap page content in a width-constrained `<main>` — full-bleed sections need `"align":"full"` on the outer block.

## Step 2b: WPBakery Has Two Edit Surfaces for the Same Page — Raw Shortcode Text (what this skill uses) and the Drag-and-Drop Backend Editor. Saving From the Drag-and-Drop Editor After a Raw-Shortcode Build Can Break the Page

**WPBakery Page Builder itself is the risk here, not Gutenberg.** Every page this skill builds is written as a raw shortcode string and pushed straight into `post_content` via REST, or via the native WP text editor view that WPBakery calls "Classic Mode" (see Step 4g — that toggle exits WPBakery's own builder UI and shows the literal `[vc_row]...[/vc_row]` text, which is what this skill edits). WPBakery *also* ships a separate drag-and-drop visual "Backend Editor" (reachable via `?wpb-backend-editor` or the page-builder toggle in wp-admin) that renders those same shortcodes as draggable visual elements, backed by a live in-browser Backbone model (`window.vc.shortcodes` — the same object Step 3b uses read-only via `singleStringify()` to construct shortcode strings safely). **Opening a page in that drag-and-drop editor and clicking Update/Save is a confirmed way to corrupt the page — the user's own words: "IF I EDIT THE BLOCKS THE WHOLE SITE EXPLODES."** Two distinct, real mechanisms explain why:

1. **Whole-tree re-serialization, not a patch.** The drag-and-drop editor doesn't save just the one element you touched — on Update it re-serializes WPBakery's *entire* in-memory shortcode model for the page back into `post_content`. Any construct in the existing raw string that the visual UI wouldn't normally produce on its own — a `<style>`-only carrier row with no visible content (Step 3), a `cz_*` theme-native element assembled via the `singleStringify` technique instead of real UI clicks (Step 3b), an attribute/value combination the builder's param UI doesn't expose a control for — is exactly the kind of content a round-trip through that model risks dropping, reordering, or mangling on save, even if you touched an unrelated element.
2. **`max_input_vars` truncation on large pages.** WPBakery's backend editor submits the whole page as one large form post, one field per shortcode parameter. A big multi-section page (very plausible for a full XD-cloned homepage) can exceed PHP's default `max_input_vars` (1000), which silently truncates the trailing form fields rather than erroring — this is a documented, independent WPBakery failure mode (not specific to this skill's raw-string approach) that resets/drops elements on save. It compounds the re-serialization risk: a page assembled by this skill, with many rows/columns/shared-style carriers, is squarely the shape of page most likely to hit this limit.

Because the shared `<style>` carrier row's CSS affects the whole page (and, if global chrome CSS ever ended up in page content instead of Additional CSS — see Step 4e — potentially more than one page), a single bad Update from the drag-and-drop editor can visibly break the page's layout/styling.

**Practical rule: once you've built or edited a page's content as a raw shortcode string (the normal mode for this skill, per Step 4g), do not open that page's drag-and-drop Backend Editor and click Update/Save yourself, even to "just check how it looks."** Viewing the live front-end page, or opening WPBakery's own Classic Mode / the text editor view (which shows/edits the same raw string you wrote, not a re-serialized version), is safe. Opening the drag-and-drop visual canvas and interacting with it (dragging, resizing, editing an element's settings panel) followed by any Save is the unsafe path.

**Tell the user explicitly, in your own words, at the end of any build/edit on a WPBakery site — this matters most the first time you build a page this way for a given site:** "This page's content was written directly as WPBakery shortcode text, not built through the drag-and-drop visual builder. If this page's editor is opened in drag-and-drop mode — dragging elements, editing them in the visual canvas — and then Update is clicked, WPBakery re-serializes the whole page from its own model and can silently break the layout or styling, especially on a page this large. To edit safely afterward, use WPBakery's Classic Mode / text editor view, or come back and ask me to edit the raw shortcode, instead of the drag-and-drop builder."

**If a page was opened in drag-and-drop mode and saved, and something now looks broken: recover from WordPress's own revision history — it's REST-reachable and does not depend on this session (or any prior session) having kept a snapshot.** Confirmed working end-to-end in this project via Application Password REST auth alone, no browser tooling needed:

1. List revisions for the page: `GET /?rest_route=/wp/v2/pages/{id}/revisions` (or `/wp/v2/posts/{id}/revisions`). Returns every saved revision — including autosaves and Update-button saves from *any* editor (Classic text view, REST, or the drag-and-drop builder) — each with `id`, `date`, `author`, `parent`. In this project a homepage with ~2 weeks of edits had 49 revisions retained.
2. Fetch a specific revision's raw content: `GET /?rest_route=/wp/v2/pages/{id}/revisions/{revision_id}&context=edit` (the `context=edit` query param is required — the default context omits the `raw` field and only returns `rendered` HTML, which is post-shortcode-processing and not directly restorable). The response's `content.raw` is the exact `post_content` string as it existed at that revision — full raw WPBakery shortcode text, byte for byte.
3. **Identify the last good revision before the drag-and-drop save by date, not by guessing which one "looks right" from a truncated preview** — pull a few candidates around the suspected break time and grep each one's `content.raw` for a known marker (a specific `el_class` name, a distinctive piece of copy) to confirm which side of the break each revision falls on.
4. Restore by pushing that revision's raw content back as the page's own current content: `POST /?rest_route=/wp/v2/pages/{id}` with `{"content": "<the raw string from step 2>"}`. This does not "revert" via any special WordPress revision-restore endpoint (there isn't a public REST one) — it's a normal content update using old content as the new value, exactly like any other push this skill makes.
5. Verify the same way as any other push (Step 5) — screenshot the live front-end at desktop and mobile widths — since the corruption's exact edges may not be obvious from the raw string alone.

This is a materially better recovery path than trying to diff against a remembered "last known-good" string, because it works even when no snapshot exists in the current conversation (a prior session's work, or a user's own drag-and-drop edit that happened with no assistant involved at all) — the revision history already has it. **A useful preventive habit given this exists: before making a large or risky change to an already-working page (a full-content rewrite, a big section replace), it costs one extra `GET` to fetch and locally note the current revision `id`/date first**, so a fast rollback target is already known rather than needing to search through possibly dozens of revisions after the fact.

## Step 2a: Build One Section at a Time, Verify Each Against XD Before Moving On

**Never write the whole page's shortcodes in one pass from a mental model of the design, publish once, and call it done.** The correct workflow, learned the hard way across many rounds of "fix this, no that's wrong too" in real sessions: build one section, publish it, screenshot the live rendered result, compare that screenshot directly against the actual XD screenshot for that same section (not memory of it — re-screenshot XD too if any time has passed), fix what doesn't match, re-screenshot, and only move to the next section once this one is confirmed correct. This is slower per-section but dramatically faster overall, because compounding small misses across many sections (wrong font sizes, wrong DOM level for a background/radius, oversized cards, missing gaps) is far more expensive to untangle after the fact than catching each one immediately.

Concretely, per section:
1. Write that section's shortcode block only (or edit it in place within the full content string if other sections already exist — never delete already-approved sections to isolate the one you're working on, see Common Mistakes).
2. Publish, then load the live front-end page and screenshot the section at real desktop width.
3. Screenshot (or re-screenshot) the matching XD section at the same relative scroll position.
4. Compare side by side for: font sizes relative to container width (not absolute px judged in isolation — a 44px heading can look right on an 1100px-wide card and oversized on a 1900px-wide full-bleed row), padding/gap proportions, border/radius/color, and DOM-level correctness (see below).
5. Only once it matches, move to the next section.

**Before writing a section's shortcode, check how the specific WPBakery element you're about to use actually behaves — don't assume from the attribute name alone.** Two concrete, repeated failure patterns from real sessions:
- **Which DOM level a param's output actually lands on.** `el_class` and the `css=""` param's generated class do NOT land on the same wrapper div (see the DOM-nesting note below) — get this wrong and a `border-radius`/`background-image`/`overflow:hidden` rule computes correctly via `getComputedStyle` but never renders visibly, because you styled the wrong nested div.
- **Whether a param needs a companion param to activate at all.** `parallax_image="ID"` does nothing on its own — it requires `parallax="content-moving"` (or another non-empty parallax mode) on the same element to enable the JS layer that actually paints it; setting `parallax_image` alone can silently no-op.

If uncertain how a given WPBakery/theme element behaves, don't guess from the attribute name — read the plugin's own PHP template if a local copy is available (`include/templates/shortcodes/vc_*.php` in `js_composer`, or search for the real source of a theme-native `cz_*` component), or search the web for the current WPBakery documentation/changelog for that specific param, rather than assuming based on a similarly-named param from a different element or an older version.

## Step 3: Build with WPBakery Shortcodes

Reference syntax (VC 9.x, current as of this writing):

```
[vc_row full_width="stretch_row" el_class="my-row-class"]
  [vc_column width="1/2"][vc_column_text]
    <h2>Heading</h2><p>Copy...</p>
  [/vc_column_text][/vc_column]
  [vc_column width="1/2"]
    [vc_single_image image="21" img_size="full" alignment="center" style="vc_box_rounded" el_class="my-custom-class"]
  [/vc_column]
[/vc_row]
```

**Never use the `css=""` shortcode attribute** — it writes into WPBakery's own generated/cached custom-CSS post meta, and updates pushed through the REST API do not reliably invalidate that cache — a `POST` can return 200 and store the new shortcode text while the page keeps rendering an older cached version of the CSS (observed concretely: a `vc_row_inner`'s `css=""` rule for `border-radius`/`box-shadow`/`background-color` silently kept serving a stale prior rule after several successful REST updates, with zero errors anywhere). There is no REST-reachable way to force-clear this cache.

**First choice for page-specific custom CSS: WPBakery's own native per-page CSS button** (and matching JS button), in the Page/Post edit screen's top toolbar, right above the WPBakery builder window — a real, dedicated per-page CSS field, not a hijacked content element. **Requires real browser tooling with a logged-in wp-admin cookie session, the same as Customizer Additional CSS (Step 4a)** — confirmed via direct REST inspection in this project that this field is NOT exposed over the REST API at all (`OPTIONS` on `/wp/v2/pages/{id}` shows only WordPress core's own `meta.footnotes` registered; no WPBakery CSS/JS meta key is `show_in_rest`), so Application-Password-only REST workflows cannot read or write it. When browser tooling + a real wp-admin login (not the Application Password) is available: open the page's edit screen, click the CSS button in the toolbar above the builder, enter plain CSS (no `<style>` tags, no `el_class` carrier-row workaround needed — this field is scoped to the page automatically), save, then verify the same way as Additional CSS (check the rendered front-end for the resulting `<style>` tag, don't assume the click "worked" from UI state alone).

**Fallback for REST/Application-Password-only workflows (no browser session): the `<style>`-in-a-hidden-`vc_column_text` carrier-row trick below.** This is a workaround for the CSS button being REST-unreachable, not a first-choice mechanism — it works reliably over plain REST calls, which is why this skill defaults to it when only Application Password credentials are available, but prefer the real per-page CSS button whenever browser tooling is on the table. Give every row/column/element that needs custom styling an `el_class`, and write plain multi-selector CSS in one shared block:

```
[vc_row el_class="my-style-carrier"][vc_column][vc_column_text]
<style>
.my-style-carrier { margin: 0 !important; padding: 0 !important; height: 0 !important; min-height: 0 !important; overflow: hidden !important; line-height: 0 !important; }
.my-style-carrier .wpb_wrapper, .my-style-carrier .wpb_text_column { margin: 0 !important; padding: 0 !important; }
.my-hero { background-image: url(...) !important; padding: 160px 0 !important; }
.my-card { border-radius: 24px !important; box-shadow: 0 20px 50px rgba(0,0,0,0.1) !important; }
.my-card img { max-height: 420px !important; object-fit: cover !important; }
</style>
[/vc_column_text][/vc_column][/vc_row]
```

**This first row must collapse to zero height itself, or it becomes a visible gap.** Even with no visible text content, a `vc_row > vc_column > vc_column_text` still renders as a real block-level element with default VC row padding/line-height — leaving it un-collapsed silently inserts a ~30-40px empty strip between the header and your first real section (easy to miss because it just looks like "some spacing," not obviously a bug, until compared pixel-for-pixel against the header's bottom edge). Give this row its own `el_class` and zero it out (`height:0 !important; overflow:hidden !important` on the row, plus zeroing the two default VC wrapper divs inside it) as part of the same shared `<style>` block it defines. Verify with `getBoundingClientRect().height` on that element after any layout complaint like "there's a gap here" — don't assume the gap is coming from the theme just because that was the cause last time.

Other gotchas that will silently break rendering:

- **`full_width="stretch_row"` is required for edge-to-edge rows.** Without it every row is boxed to the theme's content width. Design sections meant to span full viewport width (hero, CTA bands, footers) need this; two-column text+image sections usually should NOT have it (stay boxed/centered like the rest of the content column).
- **A full-bleed background with boxed inner content = nest a `vc_row_inner`/`vc_column_inner` inside the outer full-width row**, with `max-width` + `margin:auto` CSS (via `el_class`, see above) on the inner row. Don't try to fake this by both stretching and constraining the same row — the constraint just cancels the stretch.
- **A "card floating on a tinted section background" (white rounded block with a shadow, sitting on a gray/colored full-width strip) is a common pattern the first screenshot pass can miss entirely** — at a quick glance it can look like plain white content directly on plain gray. Zoom into the seam between the two backgrounds before ruling out a shadow; if there's a shadow, implement it as: outer `vc_row full_width="stretch_row"` for the tinted full-bleed background, inner `vc_row_inner` with `el_class` carrying `background-color:#fff`, `border-radius`, `box-shadow`, and its own `max-width:1200px;margin:auto` for the boxed card effect.
- **`vc_single_image` needs a real Media Library attachment ID**, not a URL. Download the image locally first, then `POST` to `wp/v2/media` with `Content-Disposition: attachment; filename=...` and `Content-Type: image/...`, read back the returned `id`, use that in `image="ID"`.
- **Uploading a local image file when only browser tooling (not curl with Application Password credentials) is available**: a page's own JS context can't read the local filesystem directly, so `fetch()`-ing a `file://` path or passing raw bytes into `evaluate_script` doesn't work cleanly (inlining base64 into a tool call is also wasteful — a single ~100KB image becomes >100K characters of context). The reliable pattern: (1) if the source image exceeds a target size limit, use `ffmpeg -i in.png -vf "scale=W:H" -c:v mjpeg -q:v 5 out.jpg` to compress **while explicitly re-specifying the original width/height in the scale filter** so dimensions are never accidentally altered — verify after with `ffprobe -show_entries stream=width,height`; (2) serve the resulting file from a short-lived local HTTP server (`python3 -m http.server` or a small custom handler) so the browser tab can `fetch()` it as a same-machine HTTP request rather than a cross-origin `file://` read; (3) **that local server needs an explicit `Access-Control-Allow-Origin: *` response header**, or the wp-admin tab's `fetch()` fails with an opaque "Failed to fetch" and no further detail (Python's plain `http.server` does not send this header by default — subclass `SimpleHTTPRequestHandler` and override `end_headers()` to add it, or use any static server with CORS enabled); (4) from the authenticated wp-admin tab, `fetch()` the image from that local server to get a `Blob`, then `fetch('/?rest_route=/wp/v2/media', {method:'POST', headers:{'Content-Type':'image/jpeg','Content-Disposition':'attachment; filename="name.jpg"','X-WP-Nonce': window.wpApiSettings.nonce}, body: blob})` — this reuses the tab's real logged-in session (via `window.wpApiSettings.nonce`), no separate Application Password needed; (5) kill the temporary local server once the upload's `id` is confirmed in the response — it should not be left running.
- **A PNG with an alpha channel (transparent corners, etc.) loses that transparency when compressed to JPEG** (flattens to white, since JPEG has no alpha support) — check `ffprobe -show_entries stream=pix_fmt` on the source first. This is usually harmless if the image sits on a plain white/matching background and the design already applies its own `border-radius` via CSS or a shortcode's rounding option (redundant with the PNG's own baked-in rounded corners), but confirm the destination section's actual background color before assuming white corners will be invisible.
- **Tall/portrait images in a two-column row will blow out row height** unless constrained. Add `content_placement="middle"` to the `vc_row` for vertical centering, and cap the image height via the `el_class` + shared `<style>` technique above (`max-height: Npx !important; object-fit: cover !important;`), not by re-cropping.
- **`loading="lazy"` on images means a fullPage screenshot taken during a fast scroll may show them as blank/missing even though they're correctly rendered.** Before concluding an image is broken, scroll it into view specifically, `sleep 1`, and check `getBoundingClientRect()` / re-screenshot at that scroll position — don't trust a single fast full-page capture.
- **`vc_btn`'s color/style params (e.g. `color="danger"`) may not visually match a specific brand hex, and VC writes its own inline `style="background-color:...; color:...;"` directly onto the `<button>` element** — inspect the rendered `outerHTML` to see it (`vc_general` computed `color` often lands on a washed-out gray like `#666`, not a real "danger" red/white). When overriding via `el_class` + the shared `<style>` block, you MUST explicitly set `color` (with `!important`) even though you only meant to change the background — an external stylesheet rule with `!important` beats the inline style, but only for the properties you actually declare; forgetting `color` leaves VC's inline gray in place while the background changes underneath it, producing a wrong-looking button that's easy to miss in a screenshot (text nearly disappears against certain backgrounds). Always verify with `getComputedStyle(...).color`, not just a visual glance.
- **Icons: check for Font Awesome before reaching for emoji or hand-drawn SVGs.** WPBakery-adjacent theme bundles (e.g. a Codevz/js_composer-style stack) often already enqueue Font Awesome site-wide. Confirm with `curl SITE/wp-content/plugins/<bundle>/.../font-awesome/css/all.min.css | grep -o 'fa-lightbulb\|fa-users\|fa-leaf...'` for the exact glyphs you need, then use `<i class="fa fa-lightbulb-o"></i>` inline in `vc_column_text` — no enqueue needed if it's already loaded. Only fall back to inline SVG if Font Awesome genuinely isn't present. Dashicons (always available, no check needed) is the next fallback, but has a much smaller icon set — verify the specific glyph exists in `wp-includes/css/dashicons.css` before committing to it.
- **When a design shows a multi-card row with only one card fully populated, do not assume the others are intentionally blank placeholders and do not invent unrelated content/colors for them.** Ask, or look for a second reference image/screenshot of that same section — XD prototypes and design handoffs often *do* have real content in every card that just wasn't visible in the first capture (wrong scroll position, viewport crop, or the file was updated between captures). When filling in matching cards, mirror the populated card's exact visual treatment (same background color, same shadow, same icon style) — do not introduce new colors or a different card style per item unless the reference explicitly shows that variation.
- **Never leave a blank line inside a `<style>` block in `vc_column_text`.** WordPress's `wpautop` filter runs on saved content and inserts `</p>\n<p>` at every double-newline it finds — including inside `<style>...</style>`, which it doesn't parse as a special context. Those literal `<`/`>` characters land inside the `<style>` element's text content as garbage CSS tokens. The browser's CSS parser hits `}</p>` mid-block, fails to recover cleanly, and silently drops some number of rules from `cssRules` — with no console error, no failed network request, and the raw HTML source (view-source or `curl`) still showing the CSS text looking completely correct, because the corruption only manifests in how the browser's *parser* consumes it, not in the text itself. This produced a real bug in this project: a header-fix `<style>` block had 3 blank lines separating logical sections (readable, felt like good style), and every rule after the first blank line — including the ones fixing the site logo image and search icon — was silently dropped, while rules before it (footer/gap fixes) worked fine. Diagnose by comparing `document.querySelector('style').textContent` (raw text, always looks right) against `Array.from(styleEl.sheet.cssRules).map(r => r.selectorText)` (parsed rules — this is where the gap shows up) via `evaluate_script`. Fix: write the entire `<style>` block as one continuous run of lines with zero blank lines from the opening `<style>` to the closing `</style>`, even across logically distinct groups of rules — use a `/* comment */` line to separate sections instead of a blank line if needed.
- **A UI element that must render above the theme's own `<header>` (e.g. a utility/top bar with corporate links and social icons) cannot be achieved by placing it earlier in page content** — page content always renders inside `<main>`/`#page_content`, below `<header>`, regardless of shortcode order. If the theme has no native top-bar toggle reachable via REST (check Step 4a first), the working technique is: give the bar `position: fixed; top:0; left:0; right:0; z-index: <high>` via `el_class` + the shared `<style>` block, and add `body { padding-top: <bar height>px !important; }` so fixed positioning doesn't overlap the real header. This was verified working end-to-end in this project once the wpautop blank-line bug (above) was also fixed — before that fix, the bar's own CSS was fine but adjacent rules elsewhere in the same corrupted style block were being dropped, which can make an unrelated fix look like it "isn't rendering" when the real fault is the parser corruption, not the fixed-positioning approach itself.

### The Real `vc_column`/`vc_row` DOM Nesting — Ground Truth From WPBakery's Own PHP Templates, Not Guessing

Confirmed by reading `js_composer/include/templates/shortcodes/vc_column.php` directly (a real copy of the plugin, not documentation) after repeatedly guessing wrong about which wrapper level a style needs to target. The actual output for `[vc_column]...[/vc_column]` is exactly three nested divs, in this order:

```
<div class="wpb_column vc_column_container ...">        <!-- el_class="" lands here -->
  <div class="vc_column-inner ...">                     <!-- css="" param's generated class lands here -->
    <div class="wpb_wrapper">                            <!-- actual shortcode content lives here -->
      ...content...
    </div>
  </div>
</div>
```

Two concrete, previously-mysterious bugs both trace back to this one fact:

1. **`el_class` and `css=""` do NOT land on the same element.** `el_class` is applied to the outer `.wpb_column` div; the `css=""` shortcode param's generated class (`vc_shortcode_custom_css_class()`) is applied one level deeper, to `.vc_column-inner`. This skill already says "never use `css=""`, use `el_class` + a shared `<style>` block" (above) — but that means **background-image, background-color, and border-radius rules meant to visually paint the column's box must target `.your-el-class .vc_column-inner` in the shared stylesheet, not `.your-el-class` directly**, because `.vc_column-inner` is the element that actually has the padding/fill and (with `parallax_image`) the background paint applied to it by the theme's own JS. Setting `border-radius`/`overflow:hidden`/`background-color` on the outer `el_class` selector alone does nothing visible if the real background paints one level deeper — the outer div stays a transparent, non-clipping wrapper around a square-cornered inner box. Symptom: you set `border-radius: 24px` via `el_class`, verify via `getComputedStyle` that the rule IS applied and IS `24px`, and the section still renders with square corners on screen — because you checked the wrong element. Always verify on `.vc_column-inner` (or whichever div actually paints), not on the element carrying your custom class.
2. **`parallax_image="ID"` does not set inline `background-image` CSS on any element in the raw template output.** It's emitted only as a `data-vc-parallax-image="<url>"` HTML attribute on the outer `.wpb_column`; a separate JS layer (skrollr, enqueued via `vc_jquery_skrollr_js`) reads that attribute at runtime and paints the actual background — meaning the visible background you're diagnosing at runtime (e.g. via `getComputedStyle(el).backgroundImage`) is a JS side-effect, not something in the shortcode's own template, and won't appear at all until that JS has run and finished laying out the parallax container. Don't be surprised that a raw HTML/curl fetch of the page shows no `background-image` anywhere near the row you set `parallax_image` on — check the *rendered* DOM in a real browser instead.

General lesson: **when a style rule computes correctly via `getComputedStyle` but still doesn't render visibly, the next suspect is not "browser bug" or "cache" — it's that you verified the wrong DOM node.** `document.elementFromPoint()` at the visual location in question, or manually walking `.wpb_column → .vc_column-inner → .wpb_wrapper` and diffing `getBoundingClientRect()`/computed background at each level, finds this class of bug in seconds instead of several rounds of blind CSS-selector guessing.

### `cz_title` and Other `cz_*` Text Elements Shrink-Wrap to Content Width by Default — `text-align: center` on an Ancestor Is Not Enough to Center Them

A `[cz_title]<h2>...</h2><p>...</p>[/cz_title]` shortcode's actual content lives inside two theme-generated wrapper divs, `.cz_title_content` → `.cz_wpe_content`, and by default **both of these wrappers size themselves to the width of their content** (effectively shrink-to-fit, e.g. via `display: table-cell` under the hood in this theme), not to 100% of their parent row/column. Concretely: if a `<p>` inside has `max-width: 600px`, the wrapping `.cz_wpe_content`/`.cz_title_content` divs compute to exactly that same ~600px width and sit flush against the left edge of their parent — `text-align: center` on the parent row does nothing, because centering inline content inside a box that's already exactly as wide as that content is a no-op. This looks visually like "the text just isn't centering," and the natural-seeming fixes (`text-align: center` on the row, on `.cz_wpe_content`, `margin: 0 auto` on the `<p>`) all silently fail for the same underlying reason: none of them address the *wrapper's own width*, which is what's actually pinning the box to the left.

Fix: force both wrapper levels to give up their shrink-to-fit sizing and take the full row width, then center content within that:

```css
.my-section .cz_title_content, .my-section .cz_wpe_content {
  display: block !important;
  width: 100% !important;
  max-width: 100% !important;
  margin: 0 !important;
  float: none !important;
  text-align: center !important;
}
```

Diagnose by checking `getBoundingClientRect()` on `.cz_wpe_content` itself (not just its child `<h2>`/`<p>`) — if its `width` matches the `<p>`'s own `max-width` almost exactly and its `x` sits flush against the parent's left padding edge, that's this bug, not a specificity/`!important` problem. Setting `width:100%` on `.cz_wpe_content` alone is not sufficient if `.cz_title_content` (its parent) is *also* shrink-wrapped — both levels need the fix, or the outer one just re-shrinks around the now-100%-wide inner one.

### `::before`/`::after` Pseudo-Elements Can Inherit `display: table` From a Clearfix Rule, Which Breaks `inset: 0` Sizing

When adding a tint/overlay pseudo-element (`.some-wrapper::before { content: ""; position: absolute; inset: 0; background: rgba(...); }`) on a WPBakery-generated wrapper div (e.g. `.vc_column-inner`), check the pseudo-element's own computed `display` before assuming `inset: 0` will size it to fill the parent. This theme (and many WPBakery-adjacent themes) applies a `::before`/`::after` clearfix rule (`content: ""; display: table;`) to common wrapper classes for old-school float-clearing — and if that rule's selector is equally or more specific than your new rule, `display: table` wins, and a `display: table` element does NOT size itself via `inset`/`top`/`right`/`bottom`/`left` the way `display: block` does — it sizes to its own (empty, since `content: ""`) intrinsic content, i.e. `0x0`. Result: `getComputedStyle(el, '::before')` shows your `background` color applied correctly and `opacity: 1`, giving no obvious sign anything is wrong, while the actual rendered overlay is invisible because it has zero width and zero height. Fix: explicitly declare `display: block !important` (or `display: absolute`'s implied block-level box) on your own `::before`/`::after` rule to beat the inherited clearfix `display: table`, and verify with `getComputedStyle(el, '::before').width`/`.height` (not just background/opacity) after any pseudo-element overlay that renders invisible with no console error.

### Multi-Column Dropdown/Mega-Menu Layouts: Use CSS Grid, Never `column-count`

If an XD mega-menu shows items split unevenly across two columns (e.g. 3 items stacked in column 1, a single distinct "external link" item alone in column 2), do NOT use CSS multi-column (`column-count: 2`) to achieve it. `column-count`'s fill order (column-major: fills column 1 top-to-bottom, then spills into column 2) is a browser-dependent behavior for edge cases — this project observed Chrome filling column-major (matching the XD reference) while Firefox filled the same markup row-major (item 1 top-left, item 2 top-right, item 3 second-row-left, etc.), producing a genuinely different, wrong-looking split with identical CSS and DOM. Confirmed via a user screenshot: same page, same CSS, different browser, different visual result.

Fix: use `display: grid` with **explicit per-item placement**, not automatic flow. Give the container `grid-template-columns: 1fr 1fr; grid-template-rows: repeat(N, auto);`, then assign every single menu item's real `grid-column`/`grid-row` individually by its stable ID (e.g. `#menu-header_2-41 { grid-column: 1; grid-row: 1; }`). This guarantees pixel-identical placement in every browser since there's no fill-order ambiguity left for the engine to resolve differently. Get the stable IDs via `GET /wp/v2/menu-items` (the numeric `id` becomes `#menu-header_2-{id}` in Superfish-style themes) — don't rely on DOM source order.

**Never combine `display: grid !important` with a menu plugin's own hide/show toggle.** Superfish-style nav plugins (and similar) toggle a submenu's visibility via an inline `style="display: none;"` / `style="display: block;"` written by JS on hover — not via a CSS class. If your stylesheet rule sets `display: grid !important` unconditionally on that same element, `!important` beats the inline `display: none`, and the dropdown renders permanently open regardless of hover state, with zero errors and a `sfHover` class that isn't even present (easy to misdiagnose as a leftover hover-state bug in your own test tooling rather than a real specificity collision). Diagnose via `getComputedStyle(el).display` vs. `el.getAttribute('style')` — if they disagree and computed wins over an inline `none`, that's this exact bug. Fix by scoping the grid layout to only apply when the toggle is already open: `.sub-menu[style*="display: block"] { display: grid !important; ...}` instead of applying `display: grid !important` unconditionally — this lets the plugin's own inline `display:none` continue to work for the closed state, and your grid layout only kicks in once the plugin itself has opened it.

## Step 4: Handle Theme Chrome Separately From Page Content

The page's own content (via `wp/v2/pages/{id}`) is independent of the active theme's header/footer:

- Classic PHP themes (like Xtra here) render their own `header.php`/`footer.php` — the header markup itself is NOT reachable via REST. But most such themes still pull their **nav menu** and **site title/logo** from standard WordPress APIs that ARE reachable — check before assuming you need a workaround:
  - `GET /wp/v2/menu-locations` lists the theme's registered nav slots (e.g. `primary`, `footer`, `mobile`) and which menu (if any) is assigned to each (`"menu": 0` = unassigned).
  - Create a real menu and populate it entirely via REST — no wp-admin clicking needed:
    ```bash
    curl -X POST ".../?rest_route=/wp/v2/menus" -d '{"name":"Primary Menu"}'   # returns id
    curl -X POST ".../?rest_route=/wp/v2/menus/{id}" -d '{"locations":["primary"]}'
    curl -X POST ".../?rest_route=/wp/v2/menu-items" -d '{"title":"About","url":"#","menus":{id},"status":"publish"}'
    ```
    Repeat the last call per nav item, in order. This is dramatically better than faking a header in page content: it's the theme's real navigation, persists correctly, and shows on every page site-wide, not just the one you're editing.
  - `POST /wp/v2/settings -d '{"title":"...", "site_logo": mediaId}'` sets the site title and logo the header actually renders (upload the logo to media library first for `site_logo`).
  - If after this the header still doesn't match (colors, layout, extra elements) — that's a deeper theme customizer/header-style setting, out of REST reach (see Step 4a below). Don't try to fix visual-only gaps by stuffing a duplicate fake header into page content — it will show ABOVE the theme's real one, not replace it.
- Block themes expose header/footer as `wp/v2/template-parts` — these ARE editable via REST (`POST` to `/wp/v2/template-parts/{theme}%2F%2F{slug}`, URL-encode the `//`). Safe to override, but changes apply site-wide, not just to one page — confirm with the user first since it's a shared template.
- **If the active theme/builder changes mid-project** (e.g. WPBakery gets installed after you already built a header/footer into page content for a block theme), strip that leftover markup out — it will duplicate the new theme's real chrome, stacking two headers or two footers visibly on the page.

## Step 3a: Theme Default Content-Wrapper Spacing

Classic PHP themes often add their own top margin/padding to the main content wrapper (e.g. Xtra's `#page_content { margin-top: 80px; }`), meant to create breathing room under a normal page title. Once you switch to a title-less/full-bleed page template, that spacing becomes an unwanted gap between the header and your first full-width row (hero image sitting well below the nav instead of flush against it). Find the actual element via `evaluate_script` walking up from your first row's `parentElement` chain checking `getComputedStyle(el).marginTop`/`paddingTop` for a nonzero value, then neutralize it with `el_class`/the shared `<style>` block (`#that-id.that-class { margin-top: 0 !important; }`) rather than assuming the theme is buggy — it's working as designed for its default use case, just not this one.

A related but distinct default-chrome gotcha: some classic themes (Xtra included) render an empty **page-title cover band** between the header and the main content on every page by default (e.g. `<div class="page_cover xtra-cover-type-title">` containing just an empty `<h2>`), styled with its own solid background color from the theme's default palette. On a title-less full-bleed front page this shows up as an unexplained flat-colored bar directly under the nav with nothing in it — easy to mistake for a leftover `<style>` bug in your own page content rather than theme default markup, since your own CSS/HTML is nowhere near it in the DOM. Diagnose via `evaluate_script` walking `header.nextElementSibling` and checking its class/background; fix the same way as other unwanted theme-default chrome — `display:none !important` via `el_class`/shared `<style>` targeting its specific class.

## Step 3b: Check for a Theme-Native Shortcode Addon Before Using Plain WPBakery Elements

Some WPBakery-integrated themes (this project's Xtra theme, by Codevz) ship their own second family of shortcodes registered into WPBakery's "Add Element" panel, visually distinguished by a **gold/orange icon color** versus WPBakery's own default blue-icon elements (e.g. "Title and Text", "Gap", "Banner", "Content Box", "Carousel" — all gold — sitting in the same picker grid as plain-icon `vc_row`/`vc_column`). **Always check for this before defaulting to generic `vc_` elements** — if the theme has its own native "Title and Text" component, that is what real site content should use, not a `vc_custom_heading` + `vc_column_text` pair assembled to approximate the same thing. This project initially built an entire homepage with `vc_custom_heading`/`vc_column_text`/`vc_btn`/hand-rolled `<div>` cards before the user pointed at a screenshot of the gold-icon grid and said "look for these golden items that's what we use not custom heading and stuff" — a direct, correct course-correction that required re-discovering the real component family and rebuilding.

**How to find the real shortcode tags behind the icons, with zero guessing:** open the real WPBakery backend editor (`?wpb-backend-editor`) and read the live in-browser shortcode registry directly via `evaluate_script` — this is faster and more reliable than reading PHP source (which may live in a separate Pro/Core plugin not available for local study):

```js
// list every registered shortcode tag + display name, theme-native ones typically share a common prefix (here, "cz_")
Object.keys(window.vc_mapper).filter(k => k.startsWith('cz_')).map(k => ({tag: k, name: window.vc_mapper[k].name}))

// get one element's full param schema (param_name, type, heading, dropdown values, dependency rules)
window.vc_mapper['cz_content_box'].params.map(p => ({param_name: p.param_name, type: p.type, heading: p.heading}))
```

`window.vc_mapper` is WPBakery's own live shortcode registry (present in any page using the backend editor) — it is ground truth for exactly what elements and params exist on *this* site's *this* plugin version, which beats reading generic documentation or a downloaded copy of core WPBakery that won't contain a theme's bundled addon shortcodes at all. A theme's free/lite distribution zip (e.g. `xtra.zip`) commonly does NOT include its own shortcode-addon plugin — it's a separate Pro/Core plugin activated by license, so don't expect to find `cz_*`-equivalent PHP source in a downloaded theme package; treat the live `vc_mapper` dump as authoritative instead.

**Getting real shortcode strings out of the schema without guessing at attribute syntax:** naive param dumps are misleading in three specific ways this project hit in sequence:

1. **`param_name` entries with `"type": "cz_title"` (or any type matching the shortcode's own tag name) are UI section-divider headings in the edit panel, not real content fields.** They have no `heading` worth reading and produce no output. A `cz_content_box` param dump showed five separate `{"param_name":"cz_title","type":"cz_title"}` entries — none of them are an actual title/text field; they're just visual dividers between the panel's tabs (Back box / Advanced / etc.).
2. **Some elements (`is_container: true` + `js_view: "VcColumnView"` in the mapper, e.g. `cz_content_box`) have NO content-bearing param at all** — their visible content (icon, title, text) comes from **nested child shortcodes inside the enclosing tags**, exactly like `vc_column` contains other elements: `[cz_content_box]...[vc_icon ...][cz_title]<h3>...</h3>[/cz_title]...[/cz_content_box]`. A live front-end render showing an empty `<span></span><div></div>` pair inside `.cz_box_front_inner` (icon slot + content slot, both empty) is the tell that the element expects nested children rather than an attribute.
3. **Some elements (`cz_title`, `cz_banner`) store their real content as enclosed shortcode body text (like `vc_column_text`), not an attribute** — even though the mapper lists a param literally named `content` with `"type": "textarea_html"`. Passing `content="<h1>...</h1>"` as a quoted attribute is wrong; the correct form is `[cz_title]<h1>...</h1>[/cz_title]`.

**The fastest way to get a 100%-correct real shortcode string for any element, with no attribute-escaping guesswork, is to build it with WPBakery's own live Backbone model and ask it to serialize itself** — this sidesteps needing to know the enclosed-vs-attribute convention, base64 vs plain-string param encoding, or exact escaping rules, because the exact same code path the visual editor itself uses does the serialization:

```js
// in the real backend editor (?wpb-backend-editor), with window.vc.shortcodes as the live Backbone collection:
const coll = window.vc.shortcodes;
const anyModel = coll.at(0);
const parentId = anyModel.get('parent'); // any valid top-level parent id works as a scratch parent
const m = coll.add({ shortcode: 'cz_content_box', parent: parentId,
  params: { class: 'my-card', content: '[vc_icon icon_fontawesome="fa fa-star"][cz_title]<h3>Title</h3><p>Body.</p>[/cz_title]' } });
const shortcodeString = coll.singleStringify(m); // <- exact, correct, real shortcode markup
coll.remove(m); // clean up the scratch model — nothing is saved server-side until a real Update click or REST POST
```

This never touches the live page content and is entirely safe to experiment with — `coll.add()`/`coll.remove()` only mutate an in-memory Backbone collection in the open tab; nothing persists unless you separately click Update or POST to REST. Note `parent` on these models takes the model's own `id` (a short UUID from `.get('id')`), not its Backbone `cid` — using the wrong one silently fails to attach a child with no error. For enclosed-body content, pass it as `params.content` in the **initial** `coll.add()` call — calling `.set('content', ...)` on an already-added model does not reliably propagate to `singleStringify`'s output.

**Confirmed real-world findings for the Xtra theme's `cz_*` shortcode family** (all obtained via the `singleStringify` method above, not guessed):

| Element (gold icon) | Real tag | Content convention | Class attribute |
|---|---|---|---|
| Title and Text | `cz_title` | Enclosed body (`[cz_title]<h1>...</h1>[/cz_title]`) — put full title+paragraph HTML directly inside, no separate text element needed | `class="..."` |
| Gap | `cz_gap` | Self-closing, all attributes: `height`, `height_tablet`, `height_mobile` (e.g. `[cz_gap height="80px" height_tablet="60px" height_mobile="40px"]`) — genuinely responsive per-breakpoint, better than a fixed-height spacer | n/a (no class param seen) |
| Content Box | `cz_content_box` | Container — nest real child shortcodes inside (`[cz_content_box]...[vc_icon][cz_title]...[/cz_title][/cz_content_box]`); this is the correct native "card" element (icon + title + text + optional link/flip-back content), not a hand-rolled `<div class="card">` | `class="..."` |
| Banner | `cz_banner` | `title` and `image` are attributes; the caption is enclosed body content (`[cz_banner title="..." image="21"]<p>Caption</p>[/cz_banner]`) — a third, different pattern from both of the above | `class="..."` |
| Button | `cz_button` | Fully attribute-based, self-closing: `title`, `link="url:#"` (WPBakery link mini-syntax), `btn_position="cz_btn_center"` etc. | `class="..."` |
| Icon (social) | `cz_social_icons` | `social` param is a WPBakery `param_group` (repeatable sub-fields `icon`/`title`/`link`/`link_target`) — **not verified working in this project**; see Common Mistakes below | `class="..."` |

**Critical, easy-to-miss inconsistency: the `cz_*` family uses `class="..."` for its custom-class attribute; plain WPBakery core shortcodes (`vc_row`, `vc_row_inner`, `vc_column`, `vc_column_inner`, `vc_single_image`, `vc_icon`, etc.) use `el_class="..."`.** These are NOT interchangeable and neither one errors when given the wrong name — the attribute is just silently ignored (or worse, silently breaks the element's own internal logic, see below), so a page can render with zero errors while several intended style hooks quietly do nothing. Always confirm via `window.vc_mapper['<tag>'].params.some(p => p.param_name === 'class' || p.param_name === 'el_class')` before assuming either name is safe for a given tag, rather than pattern-matching from a neighboring shortcode.

**A `full_width="stretch_row"` `vc_row` given `class="..."` instead of `el_class="..."` doesn't just silently drop the class — the entire row fails to render at all**, with zero console error and no trace in the rendered DOM (not even an empty wrapper). This is more severe than the usual "attribute ignored" failure mode and cost real debugging time in this project: a hero section vanished completely from the live page after a find-and-replace pass over-corrected `el_class`→`class` on `vc_row` tags in addition to the `cz_*` tags that actually needed it. Diagnose by checking the REST-fetched raw `post_content` still contains the intended shortcode (ruling out a lost edit) and then checking whether its wrapping element exists at all in the rendered DOM (ruling out a CSS-only display issue) — if the content round-trips correctly through the REST API but produces zero DOM output, suspect a wrong attribute name on a full-width/stretch row specifically, not a CSS problem.

**Prefer real native row/column features over hand-rolled CSS for common layout needs.** Before reaching for `min-height` hacks to force a row of cards to equal height, check the container shortcode's own param list — `vc_row_inner`/`vc_row` expose a native `equal_height="yes"` attribute (`window.vc_mapper['vc_row_inner'].params` shows `{"param_name":"equal_height","heading":"Equal height","type":"toggle"}`) that correctly equalizes column heights via the theme's own JS, matching what a card-grid design typically calls for without any custom CSS at all.

**`cz_social_icons`'s `social` `param_group` attribute could not be gotten to render in this project** despite confirming its expected sub-field shape (`icon`, `title`, `link`, `link_target`) and correctly base64-encoding a JSON array of them (`window.vc.utils.decodeParamValue` round-tripped it successfully, confirming the encoding format itself was right) — the element still produced zero DOM output on the live page with no error. Root cause not identified (likely a wrapper-level param, ordering requirement, or PHP-side expectation not visible from the JS mapper alone). Given this, treat `cz_social_icons` as unverified/risky for now — a plain hand-written `<a><i class="fa fa-facebook"></i></a>` set of icons inside a `vc_column_text` (as used for the utility bar) remains a safe, confirmed-working fallback for simple social icon rows; retry the native element only with time budgeted for real UI-driven trial and error (build one via actual clicks in the Add Element panel, not JS model manipulation, and read back the saved `post_content`).

## Step 3c: Prefer `el_class` + Native Column Params Over Hand-Rolled CSS Structure — WPBakery Already Has Margin/Radius/Background on Every Column

**A recurring, expensive mistake in real sessions: reaching for `position: absolute`, custom flexbox wrappers, manual class renaming, and restructured child elements to achieve a simple visual effect (a floating rounded card, a glass panel with margin) that WPBakery's own column already supports as a single element.** Per WPBakery's own "Element Design Options" (the same mechanism the `css=""` param generates — see `kb.wpbakery.com/docs/learning-more/element-design-options/`), every `vc_column`/`vc_row` supports margin (including negative), padding, border-radius, and background color/image natively, with the actual DOM content flowing normally inside — no absolute positioning needed to make a column look like an inset floating card.

Concretely, "a rounded glass panel that floats with a gap on all sides over a full-bleed photo, roughly half the row's width" is just:

```css
.my-outer-row { border-radius: 24px !important; overflow: hidden !important; }
.my-glass-panel { width: 50% !important; margin: 40px !important; background-color: rgba(30,45,70,0.4) !important; backdrop-filter: blur(16px) !important; -webkit-backdrop-filter: blur(16px) !important; border-radius: 24px !important; padding: 50px 45px !important; }
```

...applied via plain `el_class="my-glass-panel"` on a normal `[vc_column]` sitting inside a `[vc_row]` that has `parallax`/`parallax_image` (or another background mechanism) for the photo. The column's own content — `cz_title`, `cz_button`, whatever's already inside — needs zero changes: no restructuring into `vc_column_text`, no renaming existing classes the color/typography CSS already targets, no `position: absolute` + manual `top/left/bottom/width` math to fake what `margin` already does for free.

**Two concrete failure patterns from one real session, in sequence, all from skipping this check first:**
1. Tried `position: absolute` with `top/left/bottom/width` percentages on the panel to make it "float" — required guessing exact pixel offsets, produced a panel of the wrong size relative to its own text content, and broke because the row's `overflow: hidden` (needed for the photo's rounded corners) clipped the absolutely-positioned panel that was deliberately placed partially outside the row's box.
2. Nested `cz_title`/`cz_button` inside a `vc_column_text` wrapper to try to scope a single `el_class` to "just the text block" — `cz_title` and `cz_button` are theme-native elements expected as direct children of a `vc_column`/`vc_row`, not descendants of `vc_column_text`; nesting them there produced broken/tiny rendering with lost eyebrow content.
3. Renamed the column's `el_class` mid-fix (e.g. `ir-invest` → `ir-invest-panel`) without updating the pre-existing color/typography CSS rules that still referenced the old class name — text silently reverted to default black, because the "these elements already have working styling" assumption silently broke the moment the selector's own name changed.

**Before adding any structural CSS (absolute positioning, custom flex, restructured markup) to solve a "make this column look like X" problem, ask: does the column itself already support this via margin/padding/border-radius/background on its own `el_class`, using existing content unchanged?** If the answer is yes — which it almost always is for card/panel/floating-box effects — that's the entire fix. Reach for structural CSS only for effects a column's own box model genuinely cannot express (e.g. a panel that must span outside its own row's bounding box in a way padding/margin can't reach, or absolute overlays specifically needed to layer unrelated independent elements). When unsure whether a given visual effect is "just column box-model" or needs real structural CSS, search for WPBakery's own documented Element Design Options / column params first — the answer is very often already built in.

## Step 3d: Use `cz_posts` (Native Posts Grid) for Any "Card Grid of Articles/Announcements" Section — Not Hand-Typed `vc_column` Cards

**A repeating card grid of real content items (news announcements, downloads, blog posts — anything with a title, photo, date/excerpt, and a "read more" link, repeated 3+ times) is exactly what the theme's native `cz_posts` shortcode is for.** Building it by hand (one `vc_column` per card, with `vc_single_image` + manually typed `<h4><a>`/`<p>` HTML per card) works visually but throws away the entire point of a CMS — the content becomes unmanageable static text baked into one page's shortcode string instead of real WordPress posts editable from Posts → All Posts, reusable in RSS/other listings/search, with real dates and real featured images.

**`cz_posts` requires real WordPress `post` entries to source from — it is not just a layout wrapper.** If the design's "articles" are still placeholder content (as in an XD-to-WP conversion, before any real posts exist), create them first as actual Posts (title, featured image via the Set Featured Image panel, excerpt via the Excerpt panel — all reachable in the same block editor `post-new.php` screen used for pages), then reference them with the grid shortcode. Don't skip straight to hand-rolled `vc_column` cards just because "there's no real content yet" — 5 minutes creating 3 real posts up front avoids a full rebuild later once the user notices static cards should have been a real grid.

**Getting `cz_posts`'s two most important params right requires reading `window.vc_mapper['cz_posts']`'s real option values — the human-readable dropdown labels do NOT match the shortcode attribute values, and guessing a plausible-looking value (e.g. `layout="grid_1"`) will silently render wrong** (in this project, a first attempt produced one giant full-bleed image with no grid at all, because `grid_1` isn't a real value):
- `layout`: controls both column count *and* visual style in one param — the real values are compound class strings like `cz_grid_c3` (3 columns, default `cz_grid_c4` for 4), not simple names. Get the full option list via `JSON.stringify(window.vc_mapper['cz_posts'].params.find(p => p.param_name === 'layout'))` and read the `.value` object's *values* (what actually gets set), not its human-readable *keys*.
- `hover`: controls whether/where title, date, and excerpt actually render at all — several of the default-ish-looking options (e.g. `cz_grid_1_no_hover` alone) hide all text unless the user hovers, which silently produces "just photos, no visible text" on a static page nobody will hover over. For content that must always be visible (the normal case for a static content grid, not a hover-interaction gallery), use one of the `cz_grid_1_title_sub_after ...` values — these render title/meta *below* the image unconditionally, matching a typical "photo, headline, excerpt" card layout. Same lookup method: `JSON.stringify(window.vc_mapper['cz_posts'].params.find(p => p.param_name === 'hover'))`.
- As always with theme-native components, build the exact shortcode string via `window.vc.shortcodes.singleStringify()` (see Step 3b) rather than hand-typing the attribute string — this project's working, verified string ended up as `[cz_posts layout="cz_grid_c3" hover="cz_grid_1_title_sub_after cz_grid_1_has_excerpt" posts_per_page="3" class="ir-ann-grid"]`.
- The grid's own image class (`.attachment-codevz_600_600` in this theme, not a generic `.attachment-full`) needs its own `border-radius` rule via the shared `<style>` block if the design calls for rounded card photos — don't assume the theme's default grid styling already matches the specific radius/look the XD design shows.

## Step 3e: A `cz_gap` (or Any Spacing Fix) Can Silently Vanish During a Later Full-Content Rewrite — Re-Verify Standing Fixes After Big Edits

This skill's own Step 2a workflow (build a section, verify, move on) and the "full content rewrite" fallback (Step 2a / Common Mistakes, used when string-replace on a corrupted or drifted content string becomes unreliable) can quietly interact badly: a full rewrite is typically composed by re-assembling section blocks from what's *currently believed* to be the working content — and a small, easy-to-forget fix made earlier in the same session (e.g. a `[cz_gap height="40px"]` inserted between a button and the row below it) can get silently dropped if that exact rewrite pass was drafted from an earlier mental snapshot of the content rather than the literal live string. This is the same underlying risk the skill already documents for a full Additional-CSS rewrite (Step 4a) — it applies equally to page-content shortcode rewrites, and it's easy to miss because the rest of the section still looks broadly correct.

Concretely in this project: a `cz_gap` was correctly added between a "Read the 2026 report" button and a 3-card stat row, confirmed working with a screenshot — then, several unrelated fixes later (touching a completely different part of the same section), a full-content rewrite regenerated that block from an earlier draft that predated the gap fix, and the gap silently disappeared with no error, discovered only when the user pointed at a fresh screenshot showing the button flush against the cards again.

**Mitigation:** when doing a full-content rewrite that touches or is adjacent to a section with a previously-confirmed fix, explicitly re-check that fix survived the rewrite (grep the new content string for the specific `cz_gap`/class/attribute that was added) before publishing — don't assume "the rewrite was mostly copy-paste of working content" guarantees every prior fix carried over.

## Step 4a: Theme Customizer Settings Are Out of REST Reach — But Not Out of Reach Entirely

Anything stored as a `theme_mod` (header style variant, custom footer text like "© All rights reserved", color scheme picker, etc.) lives in the WordPress Customizer, not in `wp/v2/settings` or any other REST-exposed option. There is no standard REST route for theme mods, and none for the Customizer's "Additional CSS" field either (`wp_custom_css` post type has no `show_in_rest`; confirmed by checking `GET /?rest_route=/` for any `custom_css`/`wp_custom_css` route — only block-theme `wp_global_styles` routes exist, which don't apply to classic PHP themes). XML-RPC's `wp.newPost` with `post_type: custom_css` also does NOT work as a substitute — it creates an orphaned post with no effect, because Additional CSS requires updating the `custom_css_post_id` option and writing to `post_content_filtered` (not `post_content`), neither of which `wp.newPost` exposes. Verified concretely: created via XML-RPC, confirmed zero effect on the live page via a test CSS marker, then deleted the orphan.

**If you have real browser tooling and the user is willing to share the actual wp-admin login password (not the Application Password used for REST — a different credential, easy to confuse; the Application Password's *label* is not its value either), you CAN reach Additional CSS directly**, and this is meaningfully better than leaving all custom CSS stuffed in a hidden page-content row: it becomes real site-wide CSS through WordPress's own intended mechanism, independent of any single page's content surviving.
1. Log in at `/wp-login.php` with the real account credentials (chrome-devtools-mcp `fill_form` + `click` on the login button works directly — this is a real authenticated cookie session, nothing like Application Password REST auth).
2. Navigate to `/wp-admin/customize.php?autofocus[section]=custom_css` — this deep-links straight to the Additional CSS panel.
3. **Do not use the generic `fill` tool on the visible CSS textarea.** The Additional CSS field is CodeMirror-enhanced; the real interactive surface is a CodeMirror editor overlaying a hidden/inert `<textarea>`. Filling the underlying textarea via a generic form-fill tool does not update CodeMirror's internal buffer, and the visible "Publish" button stays disabled (CodeMirror's change detection didn't fire) — the text appears correct in an accessibility snapshot but has zero real effect. Instead, drive CodeMirror's own API directly via `evaluate_script`: `document.querySelector('.CodeMirror').CodeMirror.setValue(fullCssString)`. This immediately enables the Publish button (`#save`) because it's CodeMirror's own `.on('change', ...)` handler that flips it.
4. Click `#save` (Publish) via `evaluate_script` — `document.querySelector('#save').click()`. Wait ~2s, then confirm `#save` is disabled again (that means the changeset saved with no pending edits).
5. Verify the CSS is actually live server-side (not just in the Customizer's preview iframe) by checking the real front-end HTML for `<style id="wp-custom-css">` — `curl SITE | grep -o '<style id="wp-custom-css"[^>]*>'`. This is WordPress core's real Additional-CSS output tag; its presence with your rules inside confirms the save mechanism worked end-to-end (option updated, correct field written), not just a client-side preview.
6. Once confirmed live, remove any duplicate copy of the same CSS from page content (a `<style>` block in a hidden `vc_row`, etc.) so there's a single source of truth — leaving both risks silent drift between the two if either gets edited without the other.

If the user can't or won't share the real login password, fall back to the cheaper options: hide the specific unwanted element with CSS (`display:none !important` via `el_class`/shared `<style>` in page content) and build wanted content as page content instead, or ask the user to paste a CSS block into Additional CSS themselves.

**The Customizer's own themed color-picker widget (`.codevz-wp-color-picker.wp-color-picker`, a wrapper around WP's Iris/`wp-color-picker`) could not be driven programmatically in this project.** Neither directly setting `input.value` + dispatching `input`/`change`/`keyup` events, nor the documented jQuery API `jQuery(input).wpColorPicker('color', hexValue)`, actually propagated the color to the live preview — both registered a "dirty" UI state (Publish button enables) but `getComputedStyle(el).backgroundColor` inside the preview iframe's `contentDocument` stayed `rgba(0,0,0,0)`. This is a real, current automation limitation for this specific widget, not a one-off fluke — don't burn much time retrying variations of the same two approaches. **Prefer the Customizer's native styling panels for anything that isn't this specific widget** (e.g. Header - Top Bar's Container/Row inner/Left/Center/Right style cards expose real padding/margin/background popovers that DO work via UI clicks) — only fall back to Additional CSS (Step 4a above) once the color swatch itself is confirmed to be the blocker.

## Step 4d: Native Global "Header - Top Bar" (Utility Bar Above the Main Header)

Xtra (Codevz) ships a real native mechanism for a site-wide utility bar (corporate links + social icons above the main nav) — Customizer → Header → "Header - Top Bar". **Always prefer this over a hand-built page-content row for anything meant to appear above the header on every page** — a hand-built version is page-content-scoped (only shows on the one page it's built on) even if it's visually positioned to look global via `position:fixed`.

- The panel has real Add Left/Center/Right element slots. Element types include Logo, Menu, Image, Search, Button, Social Icons, Custom Template, Custom Shortcode.
- A "Menu" element's source list is populated from real registered menu locations — including theme-specific generic slots (`custom-1` through `custom-8` for Xtra) meant exactly for cases like this where there's no purpose-built location name. Discover locations via `GET /?rest_route=/wp/v2/menu-locations`.
- Build the menu entirely via REST, same pattern as Step 4's primary-nav example: `POST /?rest_route=/wp/v2/menus` (name), `POST /?rest_route=/wp/v2/menu-items` per item, then `POST /?rest_route=/wp/v2/menus/{id}` with `{"locations":["custom-1"]}` to assign it. Then in the Top Bar panel, set the Left/Right element's Menu source to "Custom 1" (matching whichever `custom-N` slot you assigned).
- A "Social Icons" element type does NOT carry its own icon data — it sources from a separate, single global list at Customizer → Header → **Social Icons** (a top-level section, distinct from Header - Top Bar). Populate icons there once and they appear wherever a Social Icons element is placed (Top Bar, footer, etc.).
- The Social Icons panel's icon-picker modal has a real working search field (`input[placeholder="Search"]`) — search by brand name (e.g. "twitter", "linkedin") to see the actual distinct icon variants available (bird vs. square-X for Twitter/X; circle vs. square for LinkedIn), rather than guessing an icon class name.
- **Adding new repeatable entries (new social icon rows, etc.): prefer the existing entry's clone/duplicate icon (`.codevz-cloneable-clone`) over the "+ Add" anchor (`.codevz-cloneable-add`).** The Add anchor is a plain `<a href="#">` whose click handler was unreliable via scripted `.click()`/`dispatchEvent()` in this project — it sometimes triggered a page-level navigation/scroll-to-top instead of firing the JS handler that actually adds a row. Cloning an existing entry and editing its fields worked reliably every time.
- **This Top Bar row's layout is `display: table` (the row) with left/right elements as `display: table-cell; vertical-align: top` — it is NOT flexbox.** Forcing `display:flex` on the table-cell elements to fix alignment issues will break the layout (content that should sit side-by-side wraps onto a new line instead). If a design needs different vertical alignment within the bar, change `vertical-align` on the table-cell (matching the real layout model) rather than converting to flex.
- A common real alignment bug: a "Social Icons" element's per-element wrapper (`.cz_elm`) can inherit the Customizer's default "Element Gap" spacing as an inline `margin-top`/`margin-bottom` (e.g. 20px) while a neighboring "Menu" element's wrapper has zero margin — this reads as "the icons and the menu text aren't lining up" even though both sit in correctly-aligned table-cells. Diagnose via `getBoundingClientRect()`/`getComputedStyle()` comparison between the two `.cz_elm` wrappers; fix by zeroing just that margin via Additional CSS targeting the specific wrapper class (e.g. `.header_1 .social_header_1_right_1 { margin-top:0 !important; margin-bottom:0 !important; }`), not by changing the row's `display` model.
- Real DOM structure for reference (Xtra, confirmed via direct inspection): `.header_1` (row) → `.row.elms_row` → `.clr` (`display:table`) → `.header_1_left`/`.header_1_right` (`display:table-cell`) → `.cz_elm` (per-element wrapper, e.g. `.menu_header_1_left_0`, `.social_header_1_right_1`) → actual content (`<ul class="sf-menu">` for a menu; `<div class="cz_social"><a class="cz-facebook">...` for icons).
- Once the native global Top Bar is confirmed live and styled correctly, remove any old hand-built page-content utility-bar row/CSS entirely — same duplicate-chrome cleanup principle as Step 4/4b.

**When rewriting Additional CSS wholesale (e.g. per a "clean this up, no comments, well-structured" request), diff-and-replace specific blocks in the actual live CSS rather than reconstructing the whole stylesheet from memory or an earlier draft.** Reconstructing from memory risks silently reverting an unrelated bug fix that was added after the version you're remembering — this happened concretely in this project: a full-CSS rewrite pass regenerated an old, unscoped `.sub-menu { display: grid !important; }` dropdown rule from an earlier mental snapshot, undoing a since-added `[style*="display: block"]` scoping fix, and the dropdowns silently started rendering permanently open again on every fresh page load. It was caught only by chance during an unrelated fresh-tab check. The safe pattern demonstrated in this session: `cm.getValue()` the real current CSS first, find the exact verbatim block to change, do a targeted string replace (aborting with an explicit error if the anchor text isn't found verbatim, rather than guessing), and `cm.setValue()` only the modified result — never regenerate the full file from scratch.

## Step 4b: Native Footer via "Footer - Custom Template" (Pro Themes)

Some premium themes (Xtra/Codevz here, Pro-license-gated) let a real WordPress page's content become the theme's actual rendered footer, instead of faking a footer inside the homepage's own page content. This is meaningfully better: it's a single shared footer across every page site-wide, editable with the same page builder, rather than a copy-pasted block duplicated per-page.

1. Build the footer's content as its own dedicated WordPress page (e.g. title "Site Footer"), using normal WPBakery shortcodes for the column layout.
2. In wp-admin → Customizer → Footer section (Pro-only — the option doesn't appear at all until the theme's Pro license is activated) → "Footer - Custom Template" → select that page from **both** the Desktop and Tablet & Mobile dropdowns.
3. **Immediately remove any hand-built footer markup from the homepage's own page content.** This is not optional cleanup — leaving it in place stacks two full footers visibly on the page (the old hand-built one plus the new Custom-Template one rendering through the theme's real `#site_footer` slot), producing an obvious duplicate-footer bug that can be non-obvious to trace back to its cause if you don't remember having built a footer in two places.
4. If an earlier CSS pass includes a rule like `#site_footer.page_footer { display: none !important; }` (written back when a hand-built footer was still in use, to hide the theme's default empty footer text) — **remove that rule once the Custom Template footer is wired up**, or it will suppress the new real footer content too, making the footer disappear entirely rather than duplicate. This exact sequence (duplicate footer → strip the page-content copy → footer vanishes → find and remove the stale `display:none` rule) happened in this project and each step looked like a different, unrelated bug until traced to its root cause.

## Step 4c: Native "Page Content Gap" Setting (WPBakery Backend Editor Only)

A classic PHP theme's default vertical spacing between header/content/footer is sometimes controllable per-page via a real, native "Page Settings" option — but it can be hidden behind a UI surface that only exists in the *real* WPBakery backend editor, not the Gutenberg-wrapped page-builder toggle most themes show by default.

- Reach it via the `?wpb-backend-editor` URL parameter on a page's edit screen (`/wp-admin/post.php?post={id}&action=edit&wpb-backend-editor`) — this is a materially different UI from the default Gutenberg editor with a "WPBakery Page Builder" toggle button; the Page Settings meta box with this option only renders in the dedicated backend-editor view.
- Look for a "Page Settings" → "General Settings" panel at the bottom of the page, containing a **"Page Content Gap"** dropdown (Xtra: default "~ Default ~" adds visible gaps; "No gap between header, content and footer" removes them entirely).
- This is the correct, native fix for a CTA-to-footer (or header-to-content) whitespace gap that persists despite zeroing out row/column padding via CSS — it controls spacing injected by the theme's own page-wrapper template, which lives outside any shortcode's own box model and can't be reached by padding/margin overrides on the content itself.
- This supersedes/complements the earlier `#page_content.page_content { margin-top: 0 !important; }` CSS override noted elsewhere in this skill — that CSS rule was a partial workaround for exactly this native setting; prefer the real Page Settings toggle when the backend editor is reachable, since it's the theme's own intended mechanism and won't fight against JS-driven layout logic the way a CSS override can.

## Step 4e: Additional CSS Is For Site-Wide Rules Only — Not Page-Specific Styling

**A recurring mistake this project made repeatedly: defaulting to Customizer Additional CSS for styling that only applies to one page's own sections (hero, cards, CTA band, etc.).** Additional CSS is real, global, site-wide CSS — the correct place for header/footer/menu/nav-mechanism fixes that must apply everywhere. It is the *wrong* place for one-page section styling like `.econet-hero-row`, `.econet-value-card`, `.econet-cta-row`, etc., even though those rules technically work there. The user explicitly corrected this mid-session: "you only go there when you're setting overall styles not one page style."

**The correct pattern (already established elsewhere in this skill, Step 3) is a shared `<style>` block inside the page's own content**, in a zero-height carrier row at the top of the page, targeting `el_class` hooks on that page's own shortcodes. This keeps page-specific CSS versioned with the page content itself (visible in the WPBakery editor, travels with the page on export/duplicate, doesn't pollute the global stylesheet) instead of living invisibly in a Customizer field disconnected from the content it styles.

- Before adding any new CSS rule, ask: does this rule need to apply on every page (header/menu/footer chrome), or only on the page currently being built (hero/card/CTA content)? Route accordingly.
- If you find yourself about to open `customize.php?autofocus[section]=custom_css` to style a `vc_row`/`cz_*` element that only exists in one page's own content, stop — use the page-content `<style>` block pattern instead.
- This project's homepage accumulated its entire `.econet-*` rule set (hero, legacy, values cards, milestone, CTA — roughly a dozen selectors) in Additional CSS across several sessions before this was caught. **Migrating an already-large accumulated block like this is real, careful work** — do it as its own deliberate pass (diff the live Additional CSS via `cm.getValue()`, move the page-specific rules into a new page-content `<style>` block via REST, verify the page still renders identically, then delete only the moved rules from Additional CSS), not as a rushed side effect of an unrelated visual fix. If a session ends before this migration is done, leave Additional CSS as the working (if architecturally wrong) source of truth rather than leaving the page half-migrated with rules split across both locations with no clear record of which is authoritative.

## Step 4f: `equal_height="yes"` Doesn't Automatically Stretch Everything Inside the Column

`vc_row_inner`/`vc_row`'s native `equal_height="yes"` (documented in Step 3b) correctly equalizes the **`.wpb_column`** elements themselves via flexbox — confirmed via `getBoundingClientRect()`, columns come out pixel-identical. But it does **not** cascade that stretched height down to a card element nested several levels inside the column (`.wpb_column` → `.vc_column-inner` → `.wpb_wrapper` → theme card wrapper → the actual visible card box) unless every element in that chain has `height: 100%`. Without it, the outer column is invisibly tall/equal while the visible card inside it still sizes to its own content and looks unequal.

- Diagnose by checking `.getBoundingClientRect().height` at each level of the DOM chain from the column down to the visible card — the mismatch (column already equal, card still not) shows up as a jump at whichever level lacks `height:100%`.
- Fix by adding `height: 100% !important; box-sizing: border-box !important;` to every wrapper level between the column and the card, scoped via `el_class`/a custom class — not by re-fighting the row's own equal-height flex mechanism with a different layout model.
- **This does not mean forcing the tallest card's height onto the others is automatically correct or automatically "too big."** If the tallest card's real content (e.g. a 4-line paragraph) needs materially more vertical room than the others, forcing equal height necessarily creates visible bottom whitespace in the shorter cards — check the actual XD reference screen for this exact section before assuming that's wrong. In this project the user twice pushed back on the resulting height ("they are too big") before it became clear via a longer dwell time on the correct XD screen (see next entry) that XD's own populated 3-card reference has the same top-aligned-content/bottom-whitespace look — the equal-height approach was right, only the absolute size (driven by padding + icon size + font-size, not by the equal-height mechanism itself) needed trimming. Prefer shrinking padding/icon size/font-size by modest increments and re-measuring the tallest card's real content height, over abandoning equal-height or fighting it with `justify-content`/`space-between` tricks, once XD confirms equal-height with top-aligned content is the intended look.
- **A single quick screenshot after scrolling to a card-grid section is not enough to conclude cards are "empty placeholders."** This project scrolled to this exact Core Values section twice earlier in the same broader effort and both times concluded (from a screenshot taken after only a 1-4 second dwell) that cards 2 and 3 were unpopulated ghost/placeholder outlines — a real, embarrassing misread corrected only when the user pointed at the same screen a third time and a longer dwell (3+ seconds settled, not just post-scroll) revealed all three cards fully populated with solid navy backgrounds and real icon/title/text content all along. The existing "wait 1-2s for fade-in" guidance elsewhere in this skill is a *minimum*, not a guarantee — if a section still looks suspiciously sparse (only one of several visually-identical cards populated) after the standard wait, treat that as a signal to wait longer and re-screenshot again, or explicitly flag the uncertainty to the user, rather than concluding "these are unpopulated by design" from limited evidence. Getting this wrong doesn't just cost a wasted screenshot — it can send an entire fix in the wrong direction (in this case, several exchanges spent debating card-height sizing against a phantom "cards 2/3 are intentionally sparse" assumption that was never true).

## Step 4g: Default to Classic Mode / Raw Shortcode Editing Over Drag-and-Drop Whenever REST/Application-Password Credentials Are Available

**Standing preference, stated explicitly by the user in this project: when you have REST API credentials (Application Password) or any other way to edit raw `post_content`, use that — not the drag-and-drop visual backend editor — by default, before the user has to ask.** Clicking through the visual panel element-by-element (opening a Content Box's settings, navigating style-kit tabs, dragging elements into rows) is slow and error-prone to automate compared to editing the shortcode string directly and pushing it via REST or the Classic Editor's WPBakery text/code toggle.

This was said reactively in this session ("you're not using drag and drop, you're using classic mode, edit the code so it's faster... also tell yourself to use classic mode than drag and drop if you've the creds") after time was spent navigating the visual panel's nested tabs looking for a style-kit control. The lesson to internalize going forward: **check for REST/Application-Password credentials first, at the start of any content-editing task, and if present, do the edit as a raw shortcode string change via REST (or the Classic Editor's text/code view) rather than opening the drag-and-drop backend editor at all.** Reach for the visual backend-editor UI only for things with no reliable raw-shortcode equivalent — Customizer settings (a different subsystem entirely, see Step 4a), or a native style-kit `sk_*` param with no documented/verified encoding (see `cz_social_icons` in Step 3b for a prior case where guessing the encoding wasted real time and never worked) — and even then, prefer building the shortcode via the `window.vc.shortcodes` Backbone-model technique (Step 3b) over UI clicks when the shortcode syntax itself is param-based and inspectable.

**This preference is not just about speed — it's a safety requirement.** The user's own confirmed experience: "I'm using WP Bakery so you're using Classic Mode and IF I EDIT THE BLOCKS THE WHOLE SITE EXPLODES." Opening WPBakery's own drag-and-drop Backend Editor on a page built as raw shortcode text and saving from it is a real, confirmed way to corrupt the page — it re-serializes the whole shortcode tree from its in-browser model and can also hit PHP's `max_input_vars` limit on a large page — not just a slower workflow. See Step 2b for the full mechanism and the mandatory warning to give the user, and always tell them explicitly not to open the drag-and-drop builder (as opposed to Classic Mode/the text view) on a page you've built this way.

## Step 4h: Confirm Which XD Screen/URL Is Actually Loaded Before Trusting What You See

XD prototype flows can link between screens, and a `navigate_page`/click during exploration can land on a completely different screen than the one intended (in this project, a scroll or stray interaction silently swapped from the homepage screen to a "Results & Reports" screen mid-session — same site, same visual language, entirely different content, and nothing in the page chrome made this obvious at a glance). Before trusting a screenshot as "the XD reference for this section," confirm the current URL matches the exact screen URL the user gave, especially after any navigation, click, or tab-switch — don't assume the tab still shows what it showed several tool calls ago.

## Step 5: Front Page and Verification

```bash
curl -s -u "user:pass" -X POST "http://SITE/?rest_route=/wp/v2/settings" \
  -H "Content-Type: application/json" -d '{"show_on_front":"page","page_on_front":PAGE_ID}'
```

Always visually verify with chrome-devtools-mcp after every content push — a 200 response from the REST API only means WordPress accepted and stored the shortcode string; it says nothing about whether VC/theme actually renders it correctly. **Verifying at desktop width alone is not sufficient — always also resize to a real mobile width (375px is a reasonable default) and check every section, not just the first one, before considering a build/fix complete.** This is a standing requirement, not an occasional nice-to-have: use `resize_page`, scroll through the full page at that width, and confirm text isn't overflowing, cards/columns stack sensibly, and nothing is clipped or overlapping. Use the real, sourced WPBakery breakpoints (480/576/768/992/1200px — see the `column_offset` section below) rather than arbitrary widths when a design calls for checking a specific tier. Two-column sections collapsing to stacked below the relevant breakpoint is correct responsive behavior, not a bug — don't "fix" it.

## Things That Are Out of Reach

- **Slider Revolution**: REST API is read-only (`GET` only on `/sliderrevolution/sliders`). No create/update route, no WP-CLI command, no documented way to author a slider except its own JS editor in wp-admin. If a design calls for a RevSlider banner, either use a plain VC row with a background image instead, or have the user build the slider once in wp-admin and hand you back its slug so you can reference it with `[rev_slider alias="slug"]`.
- **Global Styles / theme.json customizations** on a block theme require the browser-based Site Editor (cookie auth + nonces) — Application Password REST auth cannot read or write the active `wp_global_styles` post. If the user wants brand colors added as reusable palette swatches, they need to open Appearance → Editor → Styles once first; you can take it from there via REST once that record exists. (Note: this is specifically about REST auth — if you have real browser tooling and the user shares actual login credentials, the equivalent Customizer path for classic themes, Additional CSS, IS reachable this way; see Step 4a.)
- **Filesystem access to the WordPress install directory** may be explicitly off-limits (user-directory boundary) even when you can find it via the running server process (`lsof -p PID -d cwd` on a `php -S` process is a legitimate, narrow way to locate it without a broad filesystem scan — but confirm before reading/writing anything inside it).

## Common Mistakes

| Mistake | Fix |
|---|---|
| Building the whole page as one `<!-- wp:html -->` / raw HTML blob | Use native shortcodes/blocks so wp-admin's visual editor can edit it |
| Using `css=""` on any `vc_row`/`vc_row_inner`/etc., even for "simple" single-rule cases | Never use `css=""`. Prefer the real per-page CSS button (browser tooling) or `el_class` + one shared `<style>` block over REST — REST updates to `css=""` can silently serve stale cached CSS with a 200 OK and no error |
| Defaulting to the `<style>`-in-a-Text-Block carrier row when real browser tooling with a wp-admin login is available | That trick exists only because WPBakery's native per-page CSS button isn't REST-reachable (confirmed: no CSS/JS meta key is `show_in_rest`) — when a browser session is available, use the real CSS button instead, same as preferring Additional CSS-via-browser over guessing at REST workarounds |
| `vc_single_image image="https://..."` | Upload to media library first, use the numeric attachment ID |
| Judging "full width" visually without checking `full_width="stretch_row"` | Always set it explicitly per row; don't rely on defaults |
| Concluding an image is broken from one fast fullPage screenshot | Scroll to it, wait, re-check — lazy-loading is the usual culprit |
| Editing a block theme's shared header/footer template part without asking | Confirm first — it's site-wide, not page-scoped |
| Assuming the theme/builder from earlier in the session is still active | Re-check `wp/v2/plugins` and `wp/v2/themes` before every rebuild |
| Opening a raw-shortcode-built page in WPBakery's drag-and-drop Backend Editor and clicking Update, or telling the user it's safe to | It re-serializes the whole page's shortcode tree from its own model on save (and can hit PHP's `max_input_vars` on a large page) — can silently drop/mangle the shared `<style>` carrier row, `el_class`/`class` attributes, or whole rows. Only Classic Mode/the text view is safe to edit raw shortcode text in; always warn the user of this before finishing a build (Step 2b) |
| Trying to hand-diff/reconstruct a page's pre-corruption content from memory after a bad drag-and-drop save, or assuming nothing can be recovered without a session snapshot | Use `GET /wp/v2/pages/{id}/revisions` + `?context=edit` on a specific revision to get its exact raw `content.raw` — WordPress keeps these automatically regardless of which editor made the save, so a full byte-exact restore is almost always available even with zero prior session context (Step 2b) |
| Reaching for emoji or hand-rolled SVG icons by default | Check for an already-enqueued Font Awesome bundle first; use real `<i class="fa fa-...">` glyphs |
| Assuming a section with only one populated card means the rest are intentional empty placeholders | Ask, or find another capture of that section — likely all cards have real content, styled identically to the populated one |
| Trusting a single quick screenshot to rule out a box-shadow / floating-card treatment | Zoom into background-color seams specifically; shadows are easy to miss at normal screenshot scale |
| Any blank line inside a `<style>` block in page content | wpautop injects `</p><p>` at blank lines, corrupting the CSS parse and silently dropping later rules. Keep the whole style block as one continuous run of lines, no blank lines, ever |
| Pushing a header/CSS fix without re-verifying against a fresh XD screenshot when browser tools were unavailable earlier in the session | If browser tools become available again mid-task, re-check the actual XD before claiming a fix matches it — don't rely on a memory/summary of earlier findings |
| Assuming a browser MCP tool is unavailable just because an earlier ToolSearch found nothing | Re-run `claude mcp list` — a server can reconnect mid-session; if it shows Connected but ToolSearch still finds nothing, the session's tool index is stale and needs a fresh ToolSearch (or session restart) rather than more guessed query strings |
| Designing a nav dropdown/mega-menu purely from the rest of the site's visual language, without first checking whether the XD file has a real linked "open" state screen for it | Try clicking the hotspot for real (full pointer event sequence, see Step 1.6) before assuming no reference exists — an actual mega-menu screen can have very different proportions (e.g. a wide multi-column panel) than a plausible-looking guess |
| Concluding a card/section's color or content from a screenshot taken immediately after scrolling to it | Scroll-triggered fade-in animations can leave elements mid-transition (pale colors, missing icons) for 1-2s; wait and re-screenshot before treating the first capture as final |
| Treating a flat-colored, unexplained band between header and content as a bug in your own page-content CSS | Check `header.nextElementSibling` first — it may be theme-default empty chrome (e.g. Xtra's `page_cover` title band) rendered site-wide, not something your shortcodes produced |
| Using `column-count: 2` for an uneven multi-column dropdown/mega-menu layout | Use CSS Grid with explicit `grid-column`/`grid-row` per item ID instead — `column-count`'s fill order is browser-dependent and can differ between Chrome and Firefox on identical markup |
| Setting `display: grid !important` unconditionally on an element a nav plugin toggles via inline `style="display:none/block"` | Scope it to the open state only, e.g. `.sub-menu[style*="display: block"] { display: grid !important; }`, or `!important` will permanently override the plugin's closed state |
| Assuming Customizer Additional CSS is completely unreachable because REST/XML-RPC can't write it | It's reachable with real browser tooling + the actual wp-admin login password (not the Application Password) — log in, go to `customize.php?autofocus[section]=custom_css`, and drive CodeMirror's `setValue()` directly, not a generic form-fill |
| Filling the Additional CSS textarea with a generic browser-automation `fill`/`type` tool | The visible editor is CodeMirror over a hidden textarea; only `document.querySelector('.CodeMirror').CodeMirror.setValue(...)` actually registers as a change and enables Publish |
| Defaulting to `vc_custom_heading`/`vc_column_text`/`vc_btn`/hand-rolled `<div>` cards without checking for a theme-native shortcode addon first | Check the Add Element panel for a second, visually-distinct (e.g. gold-icon) family of elements — read `window.vc_mapper` for the real tag names/params rather than guessing from the icon labels |
| Treating every `param_name` in a shortcode's param dump as a real content field | Entries whose `type` matches the shortcode's own tag name (e.g. `{"param_name":"cz_title","type":"cz_title"}` inside `cz_content_box`'s own params) are UI section dividers, not fields — they produce no output |
| Assuming a shortcode's "content" param is an attribute because the mapper lists `"type": "textarea_html"` | Some elements (`cz_title`, `cz_banner`) actually store that content as enclosed shortcode body text (`[tag]...[/tag]`), not `content="..."` — verify via `coll.singleStringify()` on a real model, not by inspecting the param schema alone |
| Assuming a container element's icon/title/text come from attributes when nothing in its param list matches | Check `window.vc_mapper['<tag>'].is_container` and `.js_view` — a container element (`js_view: "VcColumnView"`) expects real nested child shortcodes between its opening/closing tags, not attribute-based content |
| Using `el_class` on every custom-styled shortcode uniformly | Verify per-tag: plain `vc_*` core shortcodes use `el_class`, while a theme's own `cz_*`-style addon family can use a plain `class` attribute instead — check `window.vc_mapper['<tag>'].params` before assuming either name, since the wrong one is silently dropped with no error |
| Seeing a section "look roughly right" after a shortcode rewrite and concluding the custom class/CSS hooks attached correctly | A shortcode's own default styling (real `<h1>`/`<button>` tags, theme base CSS) can make a section look plausible even when every custom `el_class`/`class` hook silently failed to attach — always confirm with `document.querySelector('.my-custom-class')` after any shortcode syntax change, don't trust a visual glance alone |
| Giving a `full_width="stretch_row"` `vc_row` the wrong custom-class attribute name | Unlike most silently-ignored wrong attributes, this can make the entire row disappear from rendered output with zero error — if content round-trips correctly through REST but produces no DOM output at all, suspect a wrong attribute name on a full-width row specifically |
| Forcing equal-height cards with a CSS `min-height` hack | Check for a native `equal_height="yes"` toggle on the row container shortcode first (e.g. `vc_row_inner`) — it's a real, JS-driven equalizer the theme already ships |
| Leaving a hand-built footer in page content after wiring up a theme's native "Footer - Custom Template" feature | Remove the old hand-built footer markup immediately — otherwise two footers stack visibly on the page |
| Leaving a stale `#site_footer.page_footer { display:none }` CSS rule (written for an old fake-footer setup) in place after switching to a native Custom Template footer | Remove it — it will suppress the new, correctly-wired footer content too, making the footer disappear entirely rather than duplicate |
| Trying to fix a header/footer whitespace gap purely with padding/margin CSS overrides on page content | Check for a native "Page Content Gap" option in Page Settings — reachable only via the real WPBakery backend editor (`?wpb-backend-editor`), not the default Gutenberg-wrapped toggle |
| Reconstructing a full Additional CSS rewrite from memory or an earlier draft | Diff against the actual live CSS (`cm.getValue()`) and replace only the specific block that needs to change — reconstructing from memory risks silently reverting a scoped bug fix added after the remembered version |
| Building a utility/top bar meant to appear on every page as a hand-built, `position:fixed` page-content row | Check for a native global mechanism first (e.g. Xtra's Customizer → Header → "Header - Top Bar") — a hand-built row is page-content-scoped even if visually pinned to look site-wide |
| Trying to set a Customizer color-picker's value via `input.value` + dispatched events, or jQuery's `.wpColorPicker('color', hex)` API | Both register a "dirty" UI state but don't reliably propagate to the live preview in this theme's widget — verify via `getComputedStyle` in the preview iframe before trusting either; fall back to Additional CSS if the color truly never propagates |
| Wiring up a native mechanism (e.g. Top Bar) and declaring it done because the correct data/content now renders | Structural/mechanism correctness isn't visual correctness — always diff the actual rendered styling (colors, shapes, spacing) against the real XD screen before claiming a match |
| Forcing `display:flex` on a Top Bar's left/right table-cell elements to fix alignment | This theme's Top Bar row is `display:table`/`table-cell`, not flexbox — flex-ifying the cells breaks the layout (content wraps to a new line); fix alignment with `vertical-align` or by zeroing an inherited element-gap margin instead |
| Repeatedly retrying a stuck "+ Add" cloneable-field anchor via scripted `.click()` | Use the existing entry's clone/duplicate icon (`.codevz-cloneable-clone`) instead — more reliable than fighting an `href="#"` anchor's click handler |
| Adding one-page section styling (hero/card/CTA rules) to Customizer Additional CSS by default | Additional CSS is for genuinely site-wide rules only (header/menu/footer). Page-specific styling belongs in a `<style>` block in that page's own content via `el_class`, even though Additional CSS technically works too |
| Assuming `equal_height="yes"` on a row automatically stretches a card several DOM levels deep inside each column | It only equalizes the `.wpb_column` elements themselves — add `height:100% !important` to every wrapper level between the column and the visible card, or the card stays sized to its own content while its invisible column is already equal |
| Concluding cards in a grid are "unpopulated placeholders" from a screenshot taken 1-4 seconds after scrolling to the section | If a section still looks suspiciously sparse after the standard fade-in wait, wait longer and re-screenshot again (or flag the uncertainty) before concluding the design intentionally leaves cards empty — a real per-card fade timing difference can look identical to a placeholder state |
| Opening the drag-and-drop visual backend editor to change a shortcode's content/attributes when REST or an Application Password is available | Default to editing the raw shortcode string via REST (or the Classic Editor's WPBakery text/code toggle) instead — it's faster and more reliable to automate than clicking through nested visual-panel tabs |
| Trusting a screenshot as "the XD reference" without confirming the browser is still on the exact screen URL the user gave | XD flows link between screens; a stray click/scroll/navigation can silently land on a different screen with the same visual language but entirely different content — check the URL after any navigation before treating a screenshot as ground truth |
| Setting `border-radius`/`background-color`/`overflow:hidden` via `el_class` and expecting it to paint the visible box | These land on the outer `.wpb_column`; the actual filled/clipped box is one level deeper at `.vc_column-inner`. Target `.your-el-class .vc_column-inner` in the shared stylesheet, or verify on the wrong element and conclude (wrongly) that `!important` "isn't working" |
| Expecting `parallax_image="ID"` to show up as inline `background-image` CSS in a raw HTML/curl fetch of the page | It's only a `data-vc-parallax-image` attribute in the template; a separate JS layer (skrollr) paints it at runtime. Check the live rendered DOM in a browser, not the raw server response |
| Relying on `text-align: center` on a row/column to center a `cz_title` (or other `cz_*` text element)'s heading/paragraph | `cz_title`'s `.cz_title_content`/`.cz_wpe_content` wrappers shrink-wrap to their content's width by default (e.g. matching a `<p>`'s `max-width`) and sit flush-left — centering text inside a box already exactly as wide as that text is a no-op. Force both wrapper levels to `display:block!important;width:100%!important` first, then center |
| Adding a `::before`/`::after` overlay pseudo-element to a WPBakery wrapper div and seeing it silently not render, despite `getComputedStyle` showing the right background/opacity | The wrapper may have an inherited clearfix rule setting `display:table` on `::before`/`::after`, which ignores `inset:0` sizing and computes to 0×0. Add `display:block !important` to your own rule and verify with computed `width`/`height`, not just background/opacity |
| Using REST API `wp/v2/media` (Application Password) or `window.wpApiSettings.nonce` for browser-session image uploads when neither is available/working | Fall back to the classic `async-upload.php` AJAX endpoint: grab a real `_wpnonce` from any classic admin page's upload form (`document.querySelector('input[name="_wpnonce"]').value`), then `fetch('/wp-admin/async-upload.php', {method:'POST', body: FormData with action=upload-attachment, _wpnonce, async-upload=<blob>})` — works with only a real logged-in cookie session, no REST nonce needed, and returns the same attachment `id`/`url` shape |
| Reconstructing a large multi-section rewrite by clearing the whole page down to "just the one section being fixed," planning to re-add the rest after | Don't delete working sections to isolate one for a fix — edit that section's shortcode block in place within the full content string (string-replace on a known anchor) so nothing already-approved is ever offline, even temporarily |
| Reaching for `source.unsplash.com/<w>x<h>/?keyword` for a placeholder stock photo | That endpoint is dead (returns a Heroku error page as if it were an image — check `file` on the download, not just the HTTP status). Use `picsum.photos/seed/<name>/<w>/<h>` instead for a real photographic placeholder, but it cannot guarantee subject match — confirm with the user whether random-subject photos are acceptable before spending time on this path |
| Putting `parallax_image`/background `css=""` and `el_class` for a "boxed content over full-bleed photo" section on the outer `[vc_row]` | Per the real `vc_column.php` template, these attributes belong on the inner `[vc_column]`, not the row — the row provides `full_width="stretch_row"` for bleed, the column carries the actual background/class. Getting this backwards still often visually "works" by accident (both elements nest a similar nearest-wrapper), so don't assume it's right just because it renders; check which element the attribute is actually on against the real template structure |
| Reaching for `position: absolute` + manual `top/left/bottom/width` math, custom flexbox wrappers, or renaming an element's existing `el_class` to make a column "float" as a rounded card with margin over a background | WPBakery columns already support `margin` (including making a box appear inset/floating), `border-radius`, `padding`, and `background-color` natively via `el_class` + a normal CSS rule — with content flowing in the column unchanged. Try that first; reach for absolute positioning only for effects a column's own box model genuinely can't express. Renaming an `el_class` this way also silently breaks any pre-existing CSS rules still targeting the old class name — grep the old class name before renaming it anywhere |
| Nesting `cz_title`/`cz_button` (or other theme-native container-adjacent elements) inside a `vc_column_text` to try to scope one `el_class` around "just the text" | These theme-native elements expect to be direct children of a `vc_column`/`vc_row_inner`, not descendants of `vc_column_text` — nesting them there breaks their own internal rendering (undersized boxes, lost content). Put the `el_class` on the containing `vc_column` itself instead |
| A radial-gradient `::before`/`::after` glow positioned at a row's literal corner and still invisible even after fixing the `display:table` bug | Check where the corner geometrically lands — if the row's own content (a full-height photo, an opaque card) occupies that exact corner, the glow paints underneath it and is invisible regardless of opacity. Either reposition the glow to a margin/gutter area the opaque content doesn't reach, or reconsider whether the reference actually shows two separate corner radial blobs at all — a soft diagonal `linear-gradient` wash across the whole section can look identical at a glance but requires a completely different implementation (background gradient on the section itself, not cornered pseudo-elements) |
