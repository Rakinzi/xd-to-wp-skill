Detail reference for Step 3 in SKILL.md — shortcode syntax gotchas, the real `vc_column`/`vc_row` DOM structure, the theme-native `cz_*` shortcode family, and native-vs-hand-rolled layout tradeoffs.

Everything in this file marked "confirmed from mapper" comes from that dump; everything marked "confirmed via `singleStringify`" was separately verified by building a live shortcode (see "Theme-Native Shortcode Addons" below) and reading the actual serialized output. Where a finding was never confirmed working (`cz_social_icons`), that's stated explicitly — the mapper dump gave a new lead on why, see below. **`cz_*` elements are not part of core WPBakery (`js_composer`) — they're a theme's own bundled Pro addon plugin,** so they will never appear in a downloaded copy of core WPBakery itself. A local copy of core `js_composer` (confirmed v9.0.1, matching the version this skill's other notes reference) was separately read to ground-truth the plain `vc_*` claims below — see "Core `vc_*` Params Confirmed From Source." ## Core `vc_*` Params Confirmed From Source

Read directly from `js_composer` v9.0.1's config files (`config/containers/shortcode-vc-row.php`, `config/content/vc-btn-element.php`) — these are plain WPBakery core elements (not `cz_*` theme-native ones), ground-truthing claims made elsewhere in this skill about `vc_row` and `vc_btn`:

- **`full_width` has three real values, not just `stretch_row`:** `stretch_row` (stretch row only), `stretch_row_content` (stretch row and content), `stretch_row_content_no_spaces` (stretch row and content, no paddings) — plus empty string for none. This skill's other notes only ever use `stretch_row`; the `stretch_row_content*` variants may be a more direct fix than nesting a nested `vc_row_inner`/`vc_column_inner` with manual `max-width`/`margin:auto` CSS for a "full-bleed background with boxed inner content" layout (documented above) — worth trying first before reaching for the manual nested-row workaround. WPBakery's own description warns stretching "may not work properly if parent container has `overflow: hidden`."
- **`parallax_image`'s real dependency is `parallax` (not `video_bg`), confirming the "does nothing without a parallax mode" rule stated above.** The config's `parallax` dropdown has exactly two non-empty values: `content-moving` ("Simple") and `content-moving-fade` ("With fade") — the second one isn't mentioned elsewhere in this skill and enables a fade effect alongside the parallax motion.
- **`equal_height` is a plain `toggle` param (value `"yes"`/empty), confirmed exactly as this skill already documents** — `vc_row`/`vc_row_inner` "If enabled, columns will be set to equal height," with no other hidden options or modes.
- **`vc_btn` (core WPBakery's own button element — distinct from the theme's `cz_button`) has a real, large param set**, confirmed from `config/content/vc-btn-element.php`: `title` (text), `link` (WPBakery's link mini-syntax), `shape` (`rounded`/`square`/`round`), `align`, `size` (`xs`/`sm`/`md`/`lg`), `style` (`modern`/`classic`/`flat`/`outline`/`3d`/`custom`/`outline-custom`/`gradient-custom`), `button_block` (toggle, full width), `add_icon` (toggle) plus an integrated icon-param group (`i_align`, `i_type`, `icon_fontawesome`, etc. — same shape as `vc_icon`'s own params), and style-dependent colorpicker params (`custom_background`, `custom_hover_background`, `custom_text`, `custom_hover_text`, `custom_border`, `custom_hover_border`, `gradient_custom_color_1/2`, `gradient_text_color`, `outline_custom_color`, etc.) whose visibility depends on the chosen `style` value. This confirms the "VC writes its own inline `background-color`/`color` style onto the `<button>`" behavior noted above — those inline styles are these very colorpicker params being rendered, which is why an external CSS override must explicitly re-set `color` even when only `background-color` was the intended change.

## Basic Shortcode Syntax

Reference syntax (VC 9.x, current as of this writing):

```
[vc_row full_width="stretch_row" el_class="my-row-class"]
  [vc_column width="1/2"][vc_column_text]
    <h2>Heading</h2><p>Copy...</p>
  [/vc_column_text][/vc_column]
  [vc_column width="1/2"]
    [vc_single_image image="21" img_size="full" alignment="center" style="vc_box_rounded" el_class="my-custom-class"]
  [/vc_column]
[/vc_row]
```

**Never use the `css=""` shortcode attribute** — it writes into WPBakery's own generated/cached custom-CSS post meta, and updates pushed through the REST API do not reliably invalidate that cache — a `POST` can return 200 and store the new shortcode text while the page keeps rendering an older cached version of the CSS (observed concretely: a `vc_row_inner`'s `css=""` rule for `border-radius`/`box-shadow`/`background-color` silently kept serving a stale prior rule after several successful REST updates, with zero errors anywhere). There is no REST-reachable way to force-clear this cache.

**First choice for page-specific custom CSS: WPBakery's own native per-page CSS button** (and matching JS button), in the Page/Post edit screen's top toolbar, right above the WPBakery builder window — a real, dedicated per-page CSS field, not a hijacked content element. **Requires real browser tooling with a logged-in wp-admin cookie session, the same as Customizer Additional CSS** (see `customizer.md`) — confirmed via direct REST inspection that this field is NOT exposed over the REST API at all (`OPTIONS` on `/wp/v2/pages/{id}` shows only WordPress core's own `meta.footnotes` registered; no WPBakery CSS/JS meta key is `show_in_rest`), so Application-Password-only REST workflows cannot read or write it. When browser tooling + a real wp-admin login (not the Application Password) is available: open the page's edit screen, click the CSS button in the toolbar above the builder, enter plain CSS (no `<style>` tags, no `el_class` carrier-row workaround needed — this field is scoped to the page automatically), save, then verify the same way as Additional CSS (check the rendered front-end for the resulting `<style>` tag, don't assume the click "worked" from UI state alone).

**Fallback for REST/Application-Password-only workflows (no browser session): the `<style>`-in-a-hidden-`vc_column_text` carrier-row trick below.** This is a workaround for the CSS button being REST-unreachable, not a first-choice mechanism — it works reliably over plain REST calls, which is why this skill defaults to it when only Application Password credentials are available, but prefer the real per-page CSS button whenever browser tooling is on the table. Give every row/column/element that needs custom styling an `el_class`, and write plain multi-selector CSS in one shared block:

```
[vc_row el_class="my-style-carrier"][vc_column][vc_column_text]
<style>
.my-style-carrier { margin: 0 !important; padding: 0 !important; height: 0 !important; min-height: 0 !important; overflow: hidden !important; line-height: 0 !important; }
.my-style-carrier .wpb_wrapper, .my-style-carrier .wpb_text_column { margin: 0 !important; padding: 0 !important; }
.my-hero { background-image: url(...) !important; padding: 160px 0 !important; }
.my-card { border-radius: 24px !important; box-shadow: 0 20px 50px rgba(0,0,0,0.1) !important; }
.my-card img { max-height: 420px !important; object-fit: cover !important; }
</style>
[/vc_column_text][/vc_column][/vc_row]
```

**This first row must collapse to zero height itself, or it becomes a visible gap.** Even with no visible text content, a `vc_row > vc_column > vc_column_text` still renders as a real block-level element with default VC row padding/line-height — leaving it un-collapsed silently inserts a ~30-40px empty strip between the header and your first real section (easy to miss because it just looks like "some spacing," not obviously a bug, until compared pixel-for-pixel against the header's bottom edge). Give this row its own `el_class` and zero it out (`height:0 !important; overflow:hidden !important` on the row, plus zeroing the two default VC wrapper divs inside it) as part of the same shared `<style>` block it defines. Verify with `getBoundingClientRect().height` on that element after any layout complaint like "there's a gap here" — don't assume the gap is coming from the theme just because that was the cause last time.

## Other Rendering Gotchas

- **`full_width="stretch_row"` is required for edge-to-edge rows.** Without it every row is boxed to the theme's content width. Design sections meant to span full viewport width (hero, CTA bands, footers) need this; two-column text+image sections usually should NOT have it (stay boxed/centered like the rest of the content column).
- **A full-bleed background with boxed inner content = nest a `vc_row_inner`/`vc_column_inner` inside the outer full-width row**, with `max-width` + `margin:auto` CSS (via `el_class`, see above) on the inner row. Don't try to fake this by both stretching and constraining the same row — the constraint just cancels the stretch.
- **A "card floating on a tinted section background" (white rounded block with a shadow, sitting on a gray/colored full-width strip) is a common pattern the first screenshot pass can miss entirely** — at a quick glance it can look like plain white content directly on plain gray. Zoom into the seam between the two backgrounds before ruling out a shadow; if there's a shadow, implement it as: outer `vc_row full_width="stretch_row"` for the tinted full-bleed background, inner `vc_row_inner` with `el_class` carrying `background-color:#fff`, `border-radius`, `box-shadow`, and its own `max-width:1200px;margin:auto` for the boxed card effect.
- **`vc_single_image` needs a real Media Library attachment ID**, not a URL. Download the image locally first, then `POST` to `wp/v2/media` with `Content-Disposition: attachment; filename=...` and `Content-Type: image/...`, read back the returned `id`, use that in `image="ID"`.
- **Uploading a local image file when only browser tooling (not curl with Application Password credentials) is available**: a page's own JS context can't read the local filesystem directly, so `fetch()`-ing a `file://` path or passing raw bytes into `evaluate_script` doesn't work cleanly (inlining base64 into a tool call is also wasteful — a single ~100KB image becomes >100K characters of context). The reliable pattern: (1) if the source image exceeds a target size limit, use `ffmpeg -i in.png -vf "scale=W:H" -c:v mjpeg -q:v 5 out.jpg` to compress **while explicitly re-specifying the original width/height in the scale filter** so dimensions are never accidentally altered — verify after with `ffprobe -show_entries stream=width,height`; (2) serve the resulting file from a short-lived local HTTP server (`python3 -m http.server` or a small custom handler) so the browser tab can `fetch()` it as a same-machine HTTP request rather than a cross-origin `file://` read; (3) **that local server needs an explicit `Access-Control-Allow-Origin: *` response header**, or the wp-admin tab's `fetch()` fails with an opaque "Failed to fetch" and no further detail (Python's plain `http.server` does not send this header by default — subclass `SimpleHTTPRequestHandler` and override `end_headers()` to add it, or use any static server with CORS enabled); (4) from the authenticated wp-admin tab, `fetch()` the image from that local server to get a `Blob`, then `fetch('/?rest_route=/wp/v2/media', {method:'POST', headers:{'Content-Type':'image/jpeg','Content-Disposition':'attachment; filename="name.jpg"','X-WP-Nonce': window.wpApiSettings.nonce}, body: blob})` — this reuses the tab's real logged-in session (via `window.wpApiSettings.nonce`), no separate Application Password needed; (5) kill the temporary local server once the upload's `id` is confirmed in the response — it should not be left running.
  - **If neither REST `wp/v2/media` (Application Password) nor `window.wpApiSettings.nonce` is available/working**, fall back to the classic `async-upload.php` AJAX endpoint: grab a real `_wpnonce` from any classic admin page's upload form (`document.querySelector('input[name="_wpnonce"]').value`), then `fetch('/wp-admin/async-upload.php', {method:'POST', body: FormData with action=upload-attachment, _wpnonce, async-upload=<blob>})` — works with only a real logged-in cookie session, no REST nonce needed, and returns the same attachment `id`/`url` shape.
- **A PNG with an alpha channel (transparent corners, etc.) loses that transparency when compressed to JPEG** (flattens to white, since JPEG has no alpha support) — check `ffprobe -show_entries stream=pix_fmt` on the source first. This is usually harmless if the image sits on a plain white/matching background and the design already applies its own `border-radius` via CSS or a shortcode's rounding option (redundant with the PNG's own baked-in rounded corners), but confirm the destination section's actual background color before assuming white corners will be invisible.
- **Tall/portrait images in a two-column row will blow out row height** unless constrained. Add `content_placement="middle"` to the `vc_row` for vertical centering, and cap the image height via the `el_class` + shared `<style>` technique above (`max-height: Npx !important; object-fit: cover !important;`), not by re-cropping.
- **`loading="lazy"` on images means a fullPage screenshot taken during a fast scroll may show them as blank/missing even though they're correctly rendered.** Before concluding an image is broken, scroll it into view specifically, `sleep 1`, and check `getBoundingClientRect()` / re-screenshot at that scroll position — don't trust a single fast full-page capture.
- **`vc_btn`'s color/style params (e.g. `color="danger"`) may not visually match a specific brand hex, and VC writes its own inline `style="background-color:...; color:...;"` directly onto the `<button>` element** — inspect the rendered `outerHTML` to see it (`vc_general` computed `color` often lands on a washed-out gray like `#666`, not a real "danger" red/white). When overriding via `el_class` + the shared `<style>` block, you MUST explicitly set `color` (with `!important`) even though you only meant to change the background — an external stylesheet rule with `!important` beats the inline style, but only for the properties you actually declare; forgetting `color` leaves VC's inline gray in place while the background changes underneath it, producing a wrong-looking button that's easy to miss in a screenshot (text nearly disappears against certain backgrounds). Always verify with `getComputedStyle(...).color`, not just a visual glance.
- **Icons: check for Font Awesome before reaching for emoji or hand-drawn SVGs.** WPBakery-adjacent theme bundles (e.g. a Codevz/js_composer-style stack) often already enqueue Font Awesome site-wide. Confirm with `curl SITE/wp-content/plugins/<bundle>/.../font-awesome/css/all.min.css | grep -o 'fa-lightbulb\|fa-users\|fa-leaf...'` for the exact glyphs you need, then use `<i class="fa fa-lightbulb-o"></i>` inline in `vc_column_text` — no enqueue needed if it's already loaded. Only fall back to inline SVG if Font Awesome genuinely isn't present. Dashicons (always available, no check needed) is the next fallback, but has a much smaller icon set — verify the specific glyph exists in `wp-includes/css/dashicons.css` before committing to it.
- **When a design shows a multi-card row with only one card fully populated, do not assume the others are intentionally blank placeholders and do not invent unrelated content/colors for them.** Ask, or look for a second reference image/screenshot of that same section — XD prototypes and design handoffs often *do* have real content in every card that just wasn't visible in the first capture (wrong scroll position, viewport crop, or the file was updated between captures). When filling in matching cards, mirror the populated card's exact visual treatment (same background color, same shadow, same icon style) — do not introduce new colors or a different card style per item unless the reference explicitly shows that variation.
- **Never leave a blank line inside a `<style>` block in `vc_column_text`.** WordPress's `wpautop` filter runs on saved content and inserts `</p>\n<p>` at every double-newline it finds — including inside `<style>...</style>`, which it doesn't parse as a special context. Those literal `<`/`>` characters land inside the `<style>` element's text content as garbage CSS tokens. The browser's CSS parser hits `}</p>` mid-block, fails to recover cleanly, and silently drops some number of rules from `cssRules` — with no console error, no failed network request, and the raw HTML source (view-source or `curl`) still showing the CSS text looking completely correct, because the corruption only manifests in how the browser's *parser* consumes it, not in the text itself. This produced a real bug in one project: a header-fix `<style>` block had 3 blank lines separating logical sections (readable, felt like good style), and every rule after the first blank line — including the ones fixing the site logo image and search icon — was silently dropped, while rules before it (footer/gap fixes) worked fine. Diagnose by comparing `document.querySelector('style').textContent` (raw text, always looks right) against `Array.from(styleEl.sheet.cssRules).map(r => r.selectorText)` (parsed rules — this is where the gap shows up) via `evaluate_script`. Fix: write the entire `<style>` block as one continuous run of lines with zero blank lines from the opening `<style>` to the closing `</style>`, even across logically distinct groups of rules — use a `/* comment */` line to separate sections instead of a blank line if needed.
- **A UI element that must render above the theme's own `<header>` (e.g. a utility/top bar with corporate links and social icons) cannot be achieved by placing it earlier in page content** — page content always renders inside `<main>`/`#page_content`, below `<header>`, regardless of shortcode order. If the theme has no native top-bar toggle reachable via REST (check `customizer.md` first), the working technique is: give the bar `position: fixed; top:0; left:0; right:0; z-index: <high>` via `el_class` + the shared `<style>` block, and add `body { padding-top: <bar height>px !important; }` so fixed positioning doesn't overlap the real header. This was verified working end-to-end in one project once the wpautop blank-line bug (above) was also fixed — before that fix, the bar's own CSS was fine but adjacent rules elsewhere in the same corrupted style block were being dropped, which can make an unrelated fix look like it "isn't rendering" when the real fault is the parser corruption, not the fixed-positioning approach itself.

## The Real `vc_column`/`vc_row` DOM Nesting — Ground Truth From WPBakery's Own PHP Templates, Not Guessing

Confirmed by reading `js_composer/include/templates/shortcodes/vc_column.php` directly (a real copy of the plugin, not documentation — re-verified against a downloaded `js_composer` v9.0.1 Version 6.0 package, matching the version this skill's other notes reference) after repeatedly guessing wrong about which wrapper level a style needs to target. The actual output for `[vc_column]...[/vc_column]` is exactly three nested divs, in this order:

```
<div class="wpb_column vc_column_container ...">        <!-- el_class="" lands here -->
  <div class="vc_column-inner ...">                     <!-- css="" param's generated class lands here -->
    <div class="wpb_wrapper">                            <!-- actual shortcode content lives here -->
      ...content...
    </div>
  </div>
</div>
```

Two concrete, previously-mysterious bugs both trace back to this one fact:

1. **`el_class` and `css=""` do NOT land on the same element.** `el_class` is applied to the outer `.wpb_column` div; the `css=""` shortcode param's generated class (`vc_shortcode_custom_css_class()`) is applied one level deeper, to `.vc_column-inner`. This skill already says "never use `css=""`, use `el_class` + a shared `<style>` block" (above) — but that means **background-image, background-color, and border-radius rules meant to visually paint the column's box must target `.your-el-class .vc_column-inner` in the shared stylesheet, not `.your-el-class` directly**, because `.vc_column-inner` is the element that actually has the padding/fill and (with `parallax_image`) the background paint applied to it by the theme's own JS. Setting `border-radius`/`overflow:hidden`/`background-color` on the outer `el_class` selector alone does nothing visible if the real background paints one level deeper — the outer div stays a transparent, non-clipping wrapper around a square-cornered inner box. Symptom: you set `border-radius: 24px` via `el_class`, verify via `getComputedStyle` that the rule IS applied and IS `24px`, and the section still renders with square corners on screen — because you checked the wrong element. Always verify on `.vc_column-inner` (or whichever div actually paints), not on the element carrying your custom class.
2. **`parallax_image="ID"` does not set inline `background-image` CSS on any element in the raw template output.** It's emitted only as a `data-vc-parallax-image="<url>"` HTML attribute on the outer `.wpb_column`; a separate JS layer (skrollr, enqueued via `vc_jquery_skrollr_js`) reads that attribute at runtime and paints the actual background — meaning the visible background you're diagnosing at runtime (e.g. via `getComputedStyle(el).backgroundImage`) is a JS side-effect, not something in the shortcode's own template, and won't appear at all until that JS has run and finished laying out the parallax container. Don't be surprised that a raw HTML/curl fetch of the page shows no `background-image` anywhere near the row you set `parallax_image` on — check the *rendered* DOM in a real browser instead.
   - **`parallax_image="ID"` does nothing on its own** — it requires `parallax="content-moving"` (or another non-empty parallax mode) on the same element to enable the JS layer that actually paints it; setting `parallax_image` alone can silently no-op.
   - **Per the real `vc_column.php` template, `parallax_image`/background `css=""` and `el_class` for a "boxed content over full-bleed photo" section belong on the inner `[vc_column]`, not the outer `[vc_row]`** — the row provides `full_width="stretch_row"` for bleed, the column carries the actual background/class. Getting this backwards still often visually "works" by accident (both elements nest a similar nearest-wrapper), so don't assume it's right just because it renders; check which element the attribute is actually on against the real template structure.

General lesson: **when a style rule computes correctly via `getComputedStyle` but still doesn't render visibly, the next suspect is not "browser bug" or "cache" — it's that you verified the wrong DOM node.** `document.elementFromPoint()` at the visual location in question, or manually walking `.wpb_column → .vc_column-inner → .wpb_wrapper` and diffing `getBoundingClientRect()`/computed background at each level, finds this class of bug in seconds instead of several rounds of blind CSS-selector guessing.

## `cz_title` and Other `cz_*` Text Elements Shrink-Wrap to Content Width by Default

A `[cz_title]<h2>...</h2><p>...</p>[/cz_title]` shortcode's actual content lives inside two theme-generated wrapper divs, `.cz_title_content` → `.cz_wpe_content`, and by default **both of these wrappers size themselves to the width of their content** (effectively shrink-to-fit, e.g. via `display: table-cell` under the hood in this theme), not to 100% of their parent row/column. Concretely: if a `<p>` inside has `max-width: 600px`, the wrapping `.cz_wpe_content`/`.cz_title_content` divs compute to exactly that same ~600px width and sit flush against the left edge of their parent — `text-align: center` on the parent row does nothing, because centering inline content inside a box that's already exactly as wide as that content is a no-op. This looks visually like "the text just isn't centering," and the natural-seeming fixes (`text-align: center` on the row, on `.cz_wpe_content`, `margin: 0 auto` on the `<p>`) all silently fail for the same underlying reason: none of them address the *wrapper's own width*, which is what's actually pinning the box to the left.

Fix: force both wrapper levels to give up their shrink-to-fit sizing and take the full row width, then center content within that:

```css
.my-section .cz_title_content, .my-section .cz_wpe_content {
  display: block !important;
  width: 100% !important;
  max-width: 100% !important;
  margin: 0 !important;
  float: none !important;
  text-align: center !important;
}
```

Diagnose by checking `getBoundingClientRect()` on `.cz_wpe_content` itself (not just its child `<h2>`/`<p>`) — if its `width` matches the `<p>`'s own `max-width` almost exactly and its `x` sits flush against the parent's left padding edge, that's this bug, not a specificity/`!important` problem. Setting `width:100%` on `.cz_wpe_content` alone is not sufficient if `.cz_title_content` (its parent) is *also* shrink-wrapped — both levels need the fix, or the outer one just re-shrinks around the now-100%-wide inner one.

## `::before`/`::after` Pseudo-Elements Can Inherit `display: table` From a Clearfix Rule

When adding a tint/overlay pseudo-element (`.some-wrapper::before { content: ""; position: absolute; inset: 0; background: rgba(...); }`) on a WPBakery-generated wrapper div (e.g. `.vc_column-inner`), check the pseudo-element's own computed `display` before assuming `inset: 0` will size it to fill the parent. This theme (and many WPBakery-adjacent themes) applies a `::before`/`::after` clearfix rule (`content: ""; display: table;`) to common wrapper classes for old-school float-clearing — and if that rule's selector is equally or more specific than your new rule, `display: table` wins, and a `display: table` element does NOT size itself via `inset`/`top`/`right`/`bottom`/`left` the way `display: block` does — it sizes to its own (empty, since `content: ""`) intrinsic content, i.e. `0x0`. Result: `getComputedStyle(el, '::before')` shows your `background` color applied correctly and `opacity: 1`, giving no obvious sign anything is wrong, while the actual rendered overlay is invisible because it has zero width and zero height. Fix: explicitly declare `display: block !important` (or `display: absolute`'s implied block-level box) on your own `::before`/`::after` rule to beat the inherited clearfix `display: table`, and verify with `getComputedStyle(el, '::before').width`/`.height` (not just background/opacity) after any pseudo-element overlay that renders invisible with no console error.

## Multi-Column Dropdown/Mega-Menu Layouts: Use CSS Grid, Never `column-count`

If an XD mega-menu shows items split unevenly across two columns (e.g. 3 items stacked in column 1, a single distinct "external link" item alone in column 2), do NOT use CSS multi-column (`column-count: 2`) to achieve it. `column-count`'s fill order (column-major: fills column 1 top-to-bottom, then spills into column 2) is a browser-dependent behavior for edge cases — one project observed Chrome filling column-major (matching the XD reference) while Firefox filled the same markup row-major (item 1 top-left, item 2 top-right, item 3 second-row-left, etc.), producing a genuinely different, wrong-looking split with identical CSS and DOM. Confirmed via a user screenshot: same page, same CSS, different browser, different visual result.

Fix: use `display: grid` with **explicit per-item placement**, not automatic flow. Give the container `grid-template-columns: 1fr 1fr; grid-template-rows: repeat(N, auto);`, then assign every single menu item's real `grid-column`/`grid-row` individually by its stable ID (e.g. `#menu-header_2-41 { grid-column: 1; grid-row: 1; }`). This guarantees pixel-identical placement in every browser since there's no fill-order ambiguity left for the engine to resolve differently. Get the stable IDs via `GET /wp/v2/menu-items` (the numeric `id` becomes `#menu-header_2-{id}` in Superfish-style themes) — don't rely on DOM source order.

**Never combine `display: grid !important` with a menu plugin's own hide/show toggle.** Superfish-style nav plugins (and similar) toggle a submenu's visibility via an inline `style="display: none;"` / `style="display: block;"` written by JS on hover — not via a CSS class. If your stylesheet rule sets `display: grid !important` unconditionally on that same element, `!important` beats the inline `display: none`, and the dropdown renders permanently open regardless of hover state, with zero errors and a `sfHover` class that isn't even present (easy to misdiagnose as a leftover hover-state bug in your own test tooling rather than a real specificity collision). Diagnose via `getComputedStyle(el).display` vs. `el.getAttribute('style')` — if they disagree and computed wins over an inline `none`, that's this exact bug. Fix by scoping the grid layout to only apply when the toggle is already open: `.sub-menu[style*="display: block"] { display: grid !important; ...}` instead of applying `display: grid !important` unconditionally — this lets the plugin's own inline `display:none` continue to work for the closed state, and your grid layout only kicks in once the plugin itself has opened it.

## Check for a Theme-Native Shortcode Addon Before Using Plain WPBakery Elements

Some WPBakery-integrated themes (this project's Xtra theme, by Codevz) ship their own second family of shortcodes registered into WPBakery's "Add Element" panel, visually distinguished by a **gold/orange icon color** versus WPBakery's own default blue-icon elements (e.g. "Title and Text", "Gap", "Banner", "Content Box", "Carousel" — all gold — sitting in the same picker grid as plain-icon `vc_row`/`vc_column`). **Always check for this before defaulting to generic `vc_` elements** — if the theme has its own native "Title and Text" component, that is what real site content should use, not a `vc_custom_heading` + `vc_column_text` pair assembled to approximate the same thing. One project initially built an entire homepage with `vc_custom_heading`/`vc_column_text`/`vc_btn`/hand-rolled `<div>` cards before the user pointed at a screenshot of the gold-icon grid and said "look for these golden items that's what we use not custom heading and stuff" — a direct, correct course-correction that required re-discovering the real component family and rebuilding.

**How to find the real shortcode tags behind the icons, with zero guessing:** open the real WPBakery backend editor (`?wpb-backend-editor`) and read the live in-browser shortcode registry directly via `evaluate_script` — this is faster and more reliable than reading PHP source (which may live in a separate Pro/Core plugin not available for local study):

```js
// list every registered shortcode tag + display name, theme-native ones typically share a common prefix (here, "cz_")
Object.keys(window.vc_mapper).filter(k => k.startsWith('cz_')).map(k => ({tag: k, name: window.vc_mapper[k].name}))

// get one element's full param schema (param_name, type, heading, dropdown values, dependency rules)
window.vc_mapper['cz_content_box'].params.map(p => ({param_name: p.param_name, type: p.type, heading: p.heading}))
```

`window.vc_mapper` is WPBakery's own live shortcode registry (present in any page using the backend editor) — it is ground truth for exactly what elements and params exist on *this* site's *this* plugin version, which beats reading generic documentation or a downloaded copy of core WPBakery that won't contain a theme's bundled addon shortcodes at all. A theme's free/lite distribution zip (e.g. `xtra.zip`) commonly does NOT include its own shortcode-addon plugin — it's a separate Pro/Core plugin activated by license, so don't expect to find `cz_*`-equivalent PHP source in a downloaded theme package; treat the live `vc_mapper` dump as authoritative instead. **No such dump has been saved to this repo yet — see the confidence note at the top of this file.**

**Getting real shortcode strings out of the schema without guessing at attribute syntax:** naive param dumps are misleading in three specific ways hit in sequence on one real project:

1. **`param_name` entries with `"type": "cz_title"` (or any type matching the shortcode's own tag name) are UI section-divider headings in the edit panel, not real content fields.** They have no `heading` worth reading and produce no output. A `cz_content_box` param dump showed five separate `{"param_name":"cz_title","type":"cz_title"}` entries — none of them are an actual title/text field; they're just visual dividers between the panel's tabs (Back box / Advanced / etc.).
2. **Some elements (`is_container: true` + `js_view: "VcColumnView"` in the mapper, e.g. `cz_content_box`) have NO content-bearing param at all** — their visible content (icon, title, text) comes from **nested child shortcodes inside the enclosing tags**, exactly like `vc_column` contains other elements: `[cz_content_box]...[vc_icon ...][cz_title]<h3>...</h3>[/cz_title]...[/cz_content_box]`. A live front-end render showing an empty `<span></span><div></div>` pair inside `.cz_box_front_inner` (icon slot + content slot, both empty) is the tell that the element expects nested children rather than an attribute.
3. **Some elements (`cz_title`, `cz_banner`) store their real content as enclosed shortcode body text (like `vc_column_text`), not an attribute** — even though the mapper lists a param literally named `content` with `"type": "textarea_html"`. Passing `content="<h1>...</h1>"` as a quoted attribute is wrong; the correct form is `[cz_title]<h1>...</h1>[/cz_title]`.

**The fastest way to get a 100%-correct real shortcode string for any element, with no attribute-escaping guesswork, is to build it with WPBakery's own live Backbone model and ask it to serialize itself** — this sidesteps needing to know the enclosed-vs-attribute convention, base64 vs plain-string param encoding, or exact escaping rules, because the exact same code path the visual editor itself uses does the serialization:

```js
// in the real backend editor (?wpb-backend-editor), with window.vc.shortcodes as the live Backbone collection:
const coll = window.vc.shortcodes;
const anyModel = coll.at(0);
const parentId = anyModel.get('parent'); // any valid top-level parent id works as a scratch parent
const m = coll.add({ shortcode: 'cz_content_box', parent: parentId,
  params: { class: 'my-card', content: '[vc_icon icon_fontawesome="fa fa-star"][cz_title]<h3>Title</h3><p>Body.</p>[/cz_title]' } });
const shortcodeString = coll.singleStringify(m); // <- exact, correct, real shortcode markup
coll.remove(m); // clean up the scratch model — nothing is saved server-side until a real Update click or REST POST
```

This never touches the live page content and is entirely safe to experiment with — `coll.add()`/`coll.remove()` only mutate an in-memory Backbone collection in the open tab; nothing persists unless you separately click Update or POST to REST. Note `parent` on these models takes the model's own `id` (a short UUID from `.get('id')`), not its Backbone `cid` — using the wrong one silently fails to attach a child with no error. For enclosed-body content, pass it as `params.content` in the **initial** `coll.add()` call — calling `.set('content', ...)` on an already-added model does not reliably propagate to `singleStringify`'s output.

**Critical, easy-to-miss inconsistency: the `cz_*` family uses `class="..."` for its custom-class attribute; plain WPBakery core shortcodes (`vc_row`, `vc_row_inner`, `vc_column`, `vc_column_inner`, `vc_single_image`, `vc_icon`, etc.) use `el_class="..."`.** These are NOT interchangeable and neither one errors when given the wrong name — the attribute is just silently ignored (or worse, silently breaks the element's own internal logic, see below), so a page can render with zero errors while several intended style hooks quietly do nothing. Always confirm via `window.vc_mapper['<tag>'].params.some(p => p.param_name === 'class' || p.param_name === 'el_class')` before assuming either name is safe for a given tag, rather than pattern-matching from a neighboring shortcode.

**A `full_width="stretch_row"` `vc_row` given `class="..."` instead of `el_class="..."` doesn't just silently drop the class — the entire row fails to render at all**, with zero console error and no trace in the rendered DOM (not even an empty wrapper). This is more severe than the usual "attribute ignored" failure mode and cost real debugging time in one project: a hero section vanished completely from the live page after a find-and-replace pass over-corrected `el_class`→`class` on `vc_row` tags in addition to the `cz_*` tags that actually needed it. Diagnose by checking the REST-fetched raw `post_content` still contains the intended shortcode (ruling out a lost edit) and then checking whether its wrapping element exists at all in the rendered DOM (ruling out a CSS-only display issue) — if the content round-trips correctly through the REST API but produces zero DOM output, suspect a wrong attribute name on a full-width/stretch row specifically, not a CSS problem.

**Prefer real native row/column features over hand-rolled CSS for common layout needs.** Before reaching for `min-height` hacks to force a row of cards to equal height, check the container shortcode's own param list — `vc_row_inner`/`vc_row` expose a native `equal_height="yes"` attribute (`window.vc_mapper['vc_row_inner'].params` shows `{"param_name":"equal_height","heading":"Equal height","type":"toggle"}`) that correctly equalizes column heights via the theme's own JS, matching what a card-grid design typically calls for without any custom CSS at all. See "`equal_height` Doesn't Automatically Stretch Everything" below for its limits.

**`cz_social_icons`'s `social` `param_group` attribute could not be gotten to render in one real project** despite confirming its expected sub-field shape and correctly base64-encoding a JSON array of them (`window.vc.utils.decodeParamValue` round-tripped it successfully, confirming the encoding format itself was right) — the element still produced zero DOM output on the live page with no error. **New lead from the mapper dump: `link_target` is a `checkbox` param, not a plain string field.** The earlier attempt passed `link_target` as an arbitrary string (e.g. `_blank`) inside the encoded sub-field object — a `checkbox` param in a WPBakery `param_group` typically expects the literal string `"true"` (or is omitted entirely for unchecked), not a free-form value, so this is a plausible root cause for the silent failure that wasn't visible without the mapper schema. **Next attempt should pass `link_target: "true"` (or omit the key) instead of a URL-target-style string, and build the shortcode via `singleStringify()` as before** rather than hand-encoding — this is now a concrete thing to try, not just a dead end. Until re-verified, still treat `cz_social_icons` as unconfirmed; a plain hand-written `<a><i class="fa fa-facebook"></i></a>` set of icons inside a `vc_column_text` remains the safe fallback.

## Prefer `el_class` + Native Column Params Over Hand-Rolled CSS Structure

**A recurring, expensive mistake in real sessions: reaching for `position: absolute`, custom flexbox wrappers, manual class renaming, and restructured child elements to achieve a simple visual effect (a floating rounded card, a glass panel with margin) that WPBakery's own column already supports as a single element.** Per WPBakery's own "Element Design Options" (the same mechanism the `css=""` param generates — see `kb.wpbakery.com/docs/learning-more/element-design-options/`), every `vc_column`/`vc_row` supports margin (including negative), padding, border-radius, and background color/image natively, with the actual DOM content flowing normally inside — no absolute positioning needed to make a column look like an inset floating card.

Concretely, "a rounded glass panel that floats with a gap on all sides over a full-bleed photo, roughly half the row's width" is just:

```css
.my-outer-row { border-radius: 24px !important; overflow: hidden !important; }
.my-glass-panel { width: 50% !important; margin: 40px !important; background-color: rgba(30,45,70,0.4) !important; backdrop-filter: blur(16px) !important; -webkit-backdrop-filter: blur(16px) !important; border-radius: 24px !important; padding: 50px 45px !important; }
```

...applied via plain `el_class="my-glass-panel"` on a normal `[vc_column]` sitting inside a `[vc_row]` that has `parallax`/`parallax_image` (or another background mechanism) for the photo. The column's own content — `cz_title`, `cz_button`, whatever's already inside — needs zero changes: no restructuring into `vc_column_text`, no renaming existing classes the color/typography CSS already targets, no `position: absolute` + manual `top/left/bottom/width` math to fake what `margin` already does for free.

**Two concrete failure patterns from one real session, in sequence, all from skipping this check first:**
1. Tried `position: absolute` with `top/left/bottom/width` percentages on the panel to make it "float" — required guessing exact pixel offsets, produced a panel of the wrong size relative to its own text content, and broke because the row's `overflow: hidden` (needed for the photo's rounded corners) clipped the absolutely-positioned panel that was deliberately placed partially outside the row's box.
2. Nested `cz_title`/`cz_button` inside a `vc_column_text` wrapper to try to scope a single `el_class` to "just the text block" — `cz_title` and `cz_button` are theme-native elements expected as direct children of a `vc_column`/`vc_row`, not descendants of `vc_column_text`; nesting them there produced broken/tiny rendering with lost eyebrow content.
3. Renamed the column's `el_class` mid-fix (e.g. `ir-invest` → `ir-invest-panel`) without updating the pre-existing color/typography CSS rules that still referenced the old class name — text silently reverted to default black, because the "these elements already have working styling" assumption silently broke the moment the selector's own name changed.

**Before adding any structural CSS (absolute positioning, custom flex, restructured markup) to solve a "make this column look like X" problem, ask: does the column itself already support this via margin/padding/border-radius/background on its own `el_class`, using existing content unchanged?** If the answer is yes — which it almost always is for card/panel/floating-box effects — that's the entire fix. Reach for structural CSS only for effects a column's own box model genuinely cannot express (e.g. a panel that must span outside its own row's bounding box in a way padding/margin can't reach, or absolute overlays specifically needed to layer unrelated independent elements). When unsure whether a given visual effect is "just column box-model" or needs real structural CSS, search for WPBakery's own documented Element Design Options / column params first — the answer is very often already built in.

## Use `cz_posts` (Native Posts Grid) for Any "Card Grid of Articles/Announcements" Section

**A repeating card grid of real content items (news announcements, downloads, blog posts — anything with a title, photo, date/excerpt, and a "read more" link, repeated 3+ times) is exactly what the theme's native `cz_posts` shortcode is for.** Building it by hand (one `vc_column` per card, with `vc_single_image` + manually typed `<h4><a>`/`<p>` HTML per card) works visually but throws away the entire point of a CMS — the content becomes unmanageable static text baked into one page's shortcode string instead of real WordPress posts editable from Posts → All Posts, reusable in RSS/other listings/search, with real dates and real featured images.

**`cz_posts` requires real WordPress `post` entries to source from — it is not just a layout wrapper.** If the design's "articles" are still placeholder content (as in an XD-to-WP conversion, before any real posts exist), create them first as actual Posts (title, featured image via the Set Featured Image panel, excerpt via the Excerpt panel — all reachable in the same block editor `post-new.php` screen used for pages), then reference them with the grid shortcode. Don't skip straight to hand-rolled `vc_column` cards just because "there's no real content yet" — 5 minutes creating 3 real posts up front avoids a full rebuild later once the user notices static cards should have been a real grid.

**Getting `cz_posts`'s two most important params right requires reading `window.vc_mapper['cz_posts']`'s real option values — the human-readable dropdown labels do NOT match the shortcode attribute values, and guessing a plausible-looking value (e.g. `layout="grid_1"`) will silently render wrong** (in one project, a first attempt produced one giant full-bleed image with no grid at all, because `grid_1` isn't a real value):
- `layout`: controls both column count *and* visual style in one param — the real values are compound class strings like `cz_grid_c3` (3 columns, default `cz_grid_c4` for 4), not simple names. Get the full option list via `JSON.stringify(window.vc_mapper['cz_posts'].params.find(p => p.param_name === 'layout'))` and read the `.value` object's *values* (what actually gets set), not its human-readable *keys*.
- `hover`: controls whether/where title, date, and excerpt actually render at all — several of the default-ish-looking options (e.g. `cz_grid_1_no_hover` alone) hide all text unless the user hovers, which silently produces "just photos, no visible text" on a static page nobody will hover over. For content that must always be visible (the normal case for a static content grid, not a hover-interaction gallery), use one of the `cz_grid_1_title_sub_after ...` values — these render title/meta *below* the image unconditionally, matching a typical "photo, headline, excerpt" card layout. Same lookup method: `JSON.stringify(window.vc_mapper['cz_posts'].params.find(p => p.param_name === 'hover'))`.
- As always with theme-native components, build the exact shortcode string via `window.vc.shortcodes.singleStringify()` (see above) rather than hand-typing the attribute string — one project's working, verified string ended up as `[cz_posts layout="cz_grid_c3" hover="cz_grid_1_title_sub_after cz_grid_1_has_excerpt" posts_per_page="3" class="ir-ann-grid"]`.
- The grid's own image class (`.attachment-codevz_600_600` in this theme, not a generic `.attachment-full`) needs its own `border-radius` rule via the shared `<style>` block if the design calls for rounded card photos — don't assume the theme's default grid styling already matches the specific radius/look the XD design shows.

## `equal_height="yes"` Doesn't Automatically Stretch Everything Inside the Column

`vc_row_inner`/`vc_row`'s native `equal_height="yes"` correctly equalizes the **`.wpb_column`** elements themselves via flexbox — confirmed via `getBoundingClientRect()`, columns come out pixel-identical. But it does **not** cascade that stretched height down to a card element nested several levels inside the column (`.wpb_column` → `.vc_column-inner` → `.wpb_wrapper` → theme card wrapper → the actual visible card box) unless every element in that chain has `height: 100%`. Without it, the outer column is invisibly tall/equal while the visible card inside it still sizes to its own content and looks unequal.

- Diagnose by checking `.getBoundingClientRect().height` at each level of the DOM chain from the column down to the visible card — the mismatch (column already equal, card still not) shows up as a jump at whichever level lacks `height:100%`.
- Fix by adding `height: 100% !important; box-sizing: border-box !important;` to every wrapper level between the column and the card, scoped via `el_class`/a custom class — not by re-fighting the row's own equal-height flex mechanism with a different layout model.
- **This does not mean forcing the tallest card's height onto the others is automatically correct or automatically "too big."** If the tallest card's real content (e.g. a 4-line paragraph) needs materially more vertical room than the others, forcing equal height necessarily creates visible bottom whitespace in the shorter cards — check the actual XD reference screen for this exact section before assuming that's wrong. In one project the user twice pushed back on the resulting height ("they are too big") before it became clear via a longer dwell time on the correct XD screen that XD's own populated 3-card reference has the same top-aligned-content/bottom-whitespace look — the equal-height approach was right, only the absolute size (driven by padding + icon size + font-size, not by the equal-height mechanism itself) needed trimming. Prefer shrinking padding/icon size/font-size by modest increments and re-measuring the tallest card's real content height, over abandoning equal-height or fighting it with `justify-content`/`space-between` tricks, once XD confirms equal-height with top-aligned content is the intended look.

## A Spacing Fix Can Silently Vanish During a Later Full-Content Rewrite

This skill's own workflow (build a section, verify, move on — see Step 2a in SKILL.md) and the "full content rewrite" fallback (used when string-replace on a corrupted or drifted content string becomes unreliable) can quietly interact badly: a full rewrite is typically composed by re-assembling section blocks from what's *currently believed* to be the working content — and a small, easy-to-forget fix made earlier in the same session (e.g. a `[cz_gap height="40px"]` inserted between a button and the row below it) can get silently dropped if that exact rewrite pass was drafted from an earlier mental snapshot of the content rather than the literal live string. This is the same underlying risk documented for a full Additional-CSS rewrite in `customizer.md` — it applies equally to page-content shortcode rewrites, and it's easy to miss because the rest of the section still looks broadly correct.

Concretely in one project: a `cz_gap` was correctly added between a "Read the 2026 report" button and a 3-card stat row, confirmed working with a screenshot — then, several unrelated fixes later (touching a completely different part of the same section), a full-content rewrite regenerated that block from an earlier draft that predated the gap fix, and the gap silently disappeared with no error, discovered only when the user pointed at a fresh screenshot showing the button flush against the cards again.

**Mitigation:** when doing a full-content rewrite that touches or is adjacent to a section with a previously-confirmed fix, explicitly re-check that fix survived the rewrite (grep the new content string for the specific `cz_gap`/class/attribute that was added) before publishing — don't assume "the rewrite was mostly copy-paste of working content" guarantees every prior fix carried over.
